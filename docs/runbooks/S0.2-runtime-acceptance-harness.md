# S0.2 — Disposable Runtime Acceptance Harness Runbook

**Patch baseline:** `c2cc54065cf49410538f4abed850567741dee813`
**Target environment:** Windows PowerShell 5.1+ or PowerShell 7+, Git, Node.js >=22.13.1, pnpm 12.18.0, Go 1.27.4, Docker Desktop with Compose v2.

This patch adds a repeatable owner-run acceptance harness. It does not change the backend runtime implementation and does not close S0.2 until the script passes on the owner's machine.

### 6.1 Squawk positive and negative policy tests

Install the pinned Windows binary and verify its SHA-256 before execution:

```powershell
$toolDir = Join-Path $env:LOCALAPPDATA "FlowlessHub\tools"
New-Item -ItemType Directory -Force -Path $toolDir | Out-Null
$Squawk = Join-Path $toolDir "squawk-windows-x64.exe"
$url = "https://github.com/sbdchd/squawk/releases/download/v2.72.0/squawk-windows-x64.exe"
$expectedSha256 = "dd36bf596181802b8b44512417e5ae5c133ae6be126d7563117f476ccdd9900a"

if (-not (Test-Path -LiteralPath $Squawk -PathType Leaf)) {
    $download = Join-Path $toolDir "squawk-windows-x64.download"
    $ProgressPreference = "SilentlyContinue"
    Invoke-WebRequest -Uri $url -OutFile $download -ErrorAction Stop
    $actualSha256 = (Get-FileHash -Path $download -Algorithm SHA256).Hash.ToLowerInvariant()
    if ($actualSha256 -ne $expectedSha256) {
        Remove-Item -Force $download
        throw "Squawk SHA-256 mismatch: $actualSha256"
    }
    Move-Item -Force $download $Squawk
}

$actualSha256 = (Get-FileHash -Path $Squawk -Algorithm SHA256).Hash.ToLowerInvariant()
if ($actualSha256 -ne $expectedSha256) { throw "Squawk SHA-256 mismatch: $actualSha256" }

& $Squawk --pg-version=17.0 --assume-in-transaction --include=require-timeout-settings "services/api/db/migrations/*.sql"
if ($LASTEXITCODE -ne 0) { throw "Squawk reported committed migration issues" }
```

The negative probe must fail for both timeout rules and must be deleted before continuing:

```powershell
$probe = Join-Path (Resolve-Path ".\services\api\db\migrations") "99999_squawk_negative_probe.sql"
if (Test-Path -LiteralPath $probe) { throw "Probe path already exists: $probe" }

try {
    $probeSql = @'
-- +goose Up
ALTER TABLE public.squawk_probe ADD COLUMN unsafe_text text;
'@
    [System.IO.File]::WriteAllText($probe, $probeSql, [System.Text.UTF8Encoding]::new($false))

    $probeOutput = (& $Squawk --pg-version=17.0 --assume-in-transaction --include=require-timeout-settings $probe 2>&1 | Out-String)
    $probeExit = $LASTEXITCODE
    if ($probeExit -eq 0) { throw "Squawk unexpectedly accepted the unsafe migration probe" }
    if ($probeOutput -notmatch "require-lock-timeout") { throw "Missing require-lock-timeout diagnostic`n$probeOutput" }
    if ($probeOutput -notmatch "require-statement-timeout") { throw "Missing require-statement-timeout diagnostic`n$probeOutput" }
}
finally {
    if (Test-Path -LiteralPath $probe) { Remove-Item -Force $probe }
}

& $Squawk --pg-version=17.0 --assume-in-transaction --include=require-timeout-settings "services/api/db/migrations/*.sql"
if ($LASTEXITCODE -ne 0) { throw "Committed migration lint failed after probe cleanup" }
```

The patch does not change Go, SQL, migration or generated code. These gates guard against accidental baseline drift before exercising the runtime. If sqlc generation or lint modifies tracked files, stop and isolate that drift instead of including it in this patch.

## 8. Run the automated runtime acceptance

Run the harness from the repository root:

```powershell
try {
    .\scripts\validate-s0.2-runtime.ps1 -TimeoutSeconds 300
}
catch {
    throw "S0.2 runtime acceptance failed: $($_.Exception.Message)"
}
```

The harness performs the following in order:

1. Re-check exact HEAD and ensure tracked files/index are clean.
2. Validate Compose and build the backend API, worker, and migration images.
3. Start PostgreSQL with a fresh, uniquely named disposable volume.
4. Wait for PostgreSQL health, then Goose and River migration service exit `0`, and finally PgBouncer health. Compare container timestamps to prove API/worker start only after migration completion.
5. Verify API and worker are running; check `/livez` and `/readyz`.
6. Inspect container environment to prove API connects to `pgbouncer:5432`, while the worker and migration service connect directly to `postgres:5432`.
7. Verify host port `6432` accepts a TCP connection; execute authenticated `SELECT 1` inside PgBouncer and require output `1`.
8. Stop PgBouncer and prove `/livez` stays HTTP `200` while `/readyz` becomes HTTP `503`; restart PgBouncer and require readiness recovery.
9. Require the River startup log metadata and verify no known empty-worker-bundle or missing-River-schema error appears.
10. Observe API and River worker stability and ensure neither container restart count increases during the stability window.
11. Recreate only the one-shot migration service on the same volume; Goose and River must both report success.
12. Confirm API readiness and that neither API nor worker restarted during the migration rerun.
13. Remove only the generated Compose project and its volume. Use `-KeepResources` only when deliberately retaining the disposable stack for diagnosis.

To preserve resources for troubleshooting after the run:

```powershell
.\scripts\validate-s0.2-runtime.ps1 -TimeoutSeconds 300 -KeepResources
```

The generated project name is printed by the script. Remove only that project after inspection:

```powershell
$projectName = Read-Host "Paste the disposable project name printed by the harness"
docker compose --project-name $projectName --file .\deploy\compose\backend.compose.yaml down --volumes --remove-orphans
if ($LASTEXITCODE -ne 0) { throw "Disposable project cleanup failed" }
```

Do not use `docker compose down -v` against the normal `flowlesshub-backend` project.

## 13. Checkpoint closeout criteria

S0.2 runtime acceptance may be recorded only when all of the following are true:

- The owner-run harness exits `0` on Windows/Docker from an empty disposable volume.
- Goose and River migration initial run and rerun both exit `0`.
- PgBouncer is healthy and returns `SELECT 1`; API is proven to use PgBouncer.
- River worker is proven to use direct PostgreSQL, logs successful startup, remains running and does not restart through migration rerun.
- `/livez` remains available and `/readyz` correctly transitions to `503` during dependency outage, then recovers.
- Both frontend and backend CI jobs pass on the pushed commit.
- Runtime evidence is added to the existing S0.2 slice record in a separate evidence/closeout change.

This patch does **not** tick any S0 checkbox and does not satisfy production PgBouncer, observability, reverse-proxy, Kubernetes, zero-downtime deployment, rollback rehearsal or the overall S0 exit gate.
