# S0.11 — Discord Backup Alert Integration Runbook

**Patch base:** `ce59cab21e1a2bcebd6592c9562d997a45888f74`
**Target:** Ubuntu 24.04 VPS, `/opt/flowlesshub`
**Destination:** Owner-selected Discord private channel via Incoming Webhook
**State after source patch:** Source implementation and offline tests are present; VPS credential provisioning, real Discord receipt, synthetic systemd hook tests, and owner confirmation remain pending.

This runbook is deliberately separate from the backup execution runbook. It installs only the alert script and systemd unit definitions. It does not start the backup service, activate the backup timer, change Docker/application services, or change backup/retention/R2 policies.

## 1. Security and operational boundaries

- Never paste the Discord webhook URL into ChatGPT, Git, a shell command, a command-line argument, an environment variable, CI variables, or a journal message.
- Paste the URL only into the protected credential file using a local terminal editor on the VPS.
- Treat the complete webhook URL as a password. Anyone holding it can post to its channel; rotate it immediately if exposed.
- The credential source file is `.vps-runtime/discord-webhook-url`, owned by `ubuntu:ubuntu`, mode `0600`. The notifier consumes a systemd-managed read-only credential copy through `CREDENTIALS_DIRECTORY`.
- The notifier validates the exact `discord.com` HTTPS host and webhook path, disables redirects, verifies TLS, and uses `wait=true`. A successful delivery requires HTTP 200 and a numeric Discord message ID.
- The notifier sends only static, sanitized operational text and sets `allowed_mentions.parse=[]`. It does not send archive names, checksums, database metadata, secrets, environment values, or webhook URLs.
- A transport failure never changes the result of `flowlesshub-backup.service`. The backup service and alert worker have separate systemd states and journal records.
- Only explicit Discord HTTP 429 rejection may be retried. The retry count is at most three total attempts; `Retry-After` must be present and no more than five seconds. Network errors, timeouts, redirects, server errors, and malformed responses fail without replaying a possibly delivered POST.
- The notifier has a five-second request timeout and a 30-second systemd timeout.
- Timer activation, local deletion, remote Restic pruning, application deployment, Blue/Green switching, and production backup execution are outside this runbook.

## 2. Files introduced

- `scripts/vps/backup-alert.py` — standard-library HTTPS client.
- `scripts/vps/test_backup_alert.py` — offline unit tests; makes no network request.
- `deploy/systemd/flowlesshub-backup-alert@.service` — dedicated hardened notification worker.
- `deploy/systemd/flowlesshub-backup.service` — existing service gains `OnSuccess=` and `OnFailure=` hooks.

The alert worker requires no Docker socket access and no writable access to the repository. It has its own bounded timeout, private temporary directory, strict filesystem policy, and explicit network address-family restriction.

## 8. Synthetic systemd success and failure hooks

These disposable transient units validate the systemd lifecycle integration. They do not call the production backup service or access PostgreSQL, R2, Docker, or backup artifacts.

**[VPS — UBUNTU BASH]**
**Mode:** Start two transient test units only; the failure unit is expected to exit nonzero

```bash
set -Eeuo pipefail
TEST_SINCE="$(date --iso-8601=seconds)"
sudo systemd-run --wait \
  --collect \
  --unit=flowlesshub-alert-test-success \
  --property=OnSuccess=flowlesshub-backup-alert@test-success.service \
  /usr/bin/true

if sudo systemd-run --wait \
  --collect \
  --unit=flowlesshub-alert-test-failure \
  --property=OnFailure=flowlesshub-backup-alert@test-failure.service \
  /usr/bin/false; then
  echo 'STOP: synthetic failure fixture unexpectedly exited successfully.' >&2
  exit 1
else
  echo 'Synthetic failure fixture exited nonzero as expected.'
fi

# systemd starts lifecycle handlers asynchronously; wait up to 30 seconds
# for fresh sanitized journal records from this test invocation.
for attempt in $(seq 1 30); do
  success_seen="$(sudo journalctl -u flowlesshub-backup-alert@test-success.service --since "$TEST_SINCE" --no-pager | grep -Fc 'ALERT_DELIVERY_RESULT=success event=test-success' || true)"
  failure_seen="$(sudo journalctl -u flowlesshub-backup-alert@test-failure.service --since "$TEST_SINCE" --no-pager | grep -Fc 'ALERT_DELIVERY_RESULT=success event=test-failure' || true)"
  if (( success_seen >= 1 && failure_seen >= 1 )); then break; fi
  sleep 1
done
if (( success_seen < 1 || failure_seen < 1 )); then
  echo 'STOP: synthetic systemd notifier hook did not complete within 30 seconds.' >&2
  exit 1
fi
```

Inspect both notifier units and the transient source unit results:

```bash
sudo systemctl show flowlesshub-backup-alert@test-success.service \
  -p Result -p ExecMainStatus -p ExecMainStartTimestamp
sudo systemctl show flowlesshub-backup-alert@test-failure.service \
  -p Result -p ExecMainStatus -p ExecMainStartTimestamp
sudo journalctl \
  -u flowlesshub-backup-alert@test-success.service \
  -u flowlesshub-backup-alert@test-failure.service \
  --since '15 minutes ago' --no-pager
```

Expected: both notifier units exit successfully and each emits `ALERT_DELIVERY_RESULT=success` for its matching synthetic event. Discord must visibly contain two messages explicitly labeled `TEST — SYNTHETIC SUCCESS` and `TEST — SYNTHETIC FAILURE`. The source failure fixture is expected to fail; the notifier itself must succeed. These are not real backup success/failure events.
