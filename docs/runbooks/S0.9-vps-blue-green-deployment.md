# FlowlessHub VPS Deployment Runbook — Ubuntu + Docker Compose + Nginx/Caddy Blue-Green

**Target host:** Ubuntu 24.04 LTS, existing host Nginx, Docker Engine + Compose plugin
**Domains:** `flowlesshub.com`, `app.flowlesshub.com`, `api.flowlesshub.com`
**Registry:** GHCR (`ghcr.io/weexdayend`)
**Application ports:** API container `5050`, Web container `3000`
**Private edge:** Web upstream `127.0.0.1:3032`; API upstream `127.0.0.1:5052`
**Existing Petshop ports:** web `3031`, API `5051`, PostgreSQL `5433`, Redis `6380`, Adminer `8080`
**Verified source baseline:** `main` at `e8f33bb7c0e92d4c49724dadde55d2378cbfddce` (S0.9 VPS Compose Blue-Green foundation)
**Baseline CI:** GitHub Actions run [#26](https://github.com/weexdayend/flowlesshub/actions/runs/43147198165) — frontend and backend quality gates passed on that exact commit
**Runbook refresh:** 2026-11-12 — VPS-first hardening

## 0. Safety contract

This deployment is deliberately isolated from the existing Petshop Compose project and containers.

- Do not change, recreate, stop, rename, or remove `petshop-web`, `erp-petshop-api-1`, `petshop-postgres`, `petshop-redis`, or `petshop-adminer`.
- Do not attach FlowlessHub to the `petshop-internal` network or use the Petshop PostgreSQL/Redis volumes.
- Do not use host networking. Do not publish FlowlessHub PostgreSQL/PgBouncer ports.
- Do not run broad `docker compose down`, `docker system prune`, `docker volume prune`, or `docker image prune` as part of this runbook.
- Never use `docker compose down -v` for FlowlessHub. The PostgreSQL volume is persistent data.
- Nginx remains the only public listener on host ports 80/443. Caddy binds only `127.0.0.1:3032` (web) and `127.0.0.1:5052` (API); it has no public TLS listener.
- All commands are project-scoped to `deploy/compose/vps.compose.yaml` and a dedicated Compose project/network/volume.
- Run the deployment as the normal Docker operator (`ubuntu` in the supplied host output). Use `sudo` only for host Nginx/Certbot/system inspection.

The current API implementation exposes `/livez` and `/readyz`. It does not yet expose business endpoints or a CORS policy. The API hostname is configured now for future use and health validation; this deployment does not claim that a complete business API already exists. Before browser code at `flowlesshub.com` or `app.flowlesshub.com` calls cross-origin business endpoints at `api.flowlesshub.com`, add an explicit CORS allowlist for those two HTTPS origins (or adopt a same-origin API path). The frontend currently renders the foundation workspace; it does not yet prove end-to-end business workflows.

## 1. Architecture

```text
Internet
  |
  +-- flowlesshub.com / app.flowlesshub.com / api.flowlesshub.com
  |
Host Nginx :80/:443  (existing service, owns TLS)
  |
  +-- flowlesshub.com / app.flowlesshub.com -> 127.0.0.1:3032
  |       Caddy :3032 -> active web color :3000
  |
  +-- api.flowlesshub.com -> 127.0.0.1:5052
          Caddy :5052 -> active API color :5050

Blue/green candidates live on the private Compose edge network.

Private backend network:
  API -> PgBouncer:6432 -> FlowlessHub PostgreSQL:5432
  Worker -> PostgreSQL:5432 (direct session connection)
  Migration -> PostgreSQL:5432 (direct session connection)
```

FlowlessHub has its own `flowlesshub-vps` Compose project, `flowlesshub-vps-edge` and `flowlesshub-vps-backend` networks, `flowlesshub-vps-postgres-data` volume, and Web cache volumes. The backend network is internal. No FlowlessHub database port is published to the host or Internet.

Nginx routes the two web hostnames to Caddy :3032 and the API hostname to Caddy :5052. Caddy switches Web and API together to the same active color using one validated config. This keeps existing Frictiona/Petshop Nginx server blocks unchanged while retaining a Caddy-controlled blue-green switch.

## 2. Capacity policy for the current 2 GiB VPS

The host snapshot showed approximately 100 MiB combined Petshop container usage at that instant and approximately 29 GiB free disk. An earlier `free -h` snapshot showed around 591 MiB available RAM; this must be measured again immediately before deployment. Docker reported 7.779 GiB BuildKit cache, but this runbook does not prune it.

The Compose resource ceilings are intentionally constrained (PostgreSQL 384 MiB, PgBouncer 64 MiB, each API 96 MiB, each Web 256 MiB, worker 96 MiB, Caddy 64 MiB). These are ceilings, not guaranteed real usage or a RAM reservation.

- Initial single-color deployment refuses to proceed below 256 MiB `MemAvailable`.
- Starting a stopped blue-green candidate requires `FLOWLESSHUB_MIN_AVAILABLE_MIB` (default 384 MiB) before starting the inactive color. Reusing an already-running inactive color skips this additional-start guard because it does not add another API/Web pair.
- After candidate startup/reuse, traffic switching is refused if `MemAvailable` falls below 256 MiB. Only the inactive candidate is stopped; the active color remains running.
- If the guard refuses a blue-green overlap, do not lower the threshold just to force deployment. Upgrade RAM or reduce unrelated host workloads after an explicit review.
- A 2 GiB VPS is a constrained first-production target. Monitor `docker stats`, `/proc/meminfo`, swap, and OOM logs. Do not promise zero-downtime blue-green under memory pressure.

## 3. VPS-first release workflow — Windows developer workstation + GitHub Actions

**Policy:** local runtime testing is not a required gate. The developer workstation is used for repository edits, Git, patch application, review, and push. GitHub Actions owns source/configuration quality gates and release image builds. The VPS is the integration/runtime environment for candidate deployment, smoke tests, traffic switching, and rollback.

Do not build Docker images on the 2 GiB VPS or require Docker Desktop on the Windows workstation. The CI job validates the VPS shell scripts, Docker Compose model, both Caddy configurations, and the additive Nginx virtual host in GitHub-hosted runners.

### 3.1 Apply the VPS-first hardening patch

The S0.9 Compose Blue-Green foundation is already committed on `main` at `e8f33bb7c0e92d4c49724dadde55d2378cbfddce`; run [#26](https://github.com/weexdayend/flowlesshub/actions/runs/43147198165) passed. This incremental hardening patch is based on that exact commit. It does not recreate the S0.9 files already in the repository.

Download `FLOWLESSHUB-S0.9-VPS-FIRST-HARDENING.patch`. If the browser saves it in the repository root, move it to `%TEMP%` before checking Git cleanliness. Never stage a `.patch` file.

Run this from the repository root in Windows PowerShell:

```powershell
$ErrorActionPreference = "Stop"
$repoRoot = (git rev-parse --show-toplevel).Trim()
if ($LASTEXITCODE -ne 0) { throw "Not inside a Git repository." }
Set-Location $repoRoot

$patchName = "FLOWLESSHUB-S0.9-VPS-FIRST-HARDENING.patch"
$patchInRepo = Join-Path $repoRoot $patchName
$patchInTemp = Join-Path $env:TEMP $patchName

if (Test-Path $patchInRepo) {
    if (Test-Path $patchInTemp) {
        $repoHash = (Get-FileHash $patchInRepo -Algorithm SHA256).Hash
        $tempHash = (Get-FileHash $patchInTemp -Algorithm SHA256).Hash
        if ($repoHash -ne $tempHash) { throw "A different patch already exists in TEMP. Inspect both files." }
        Remove-Item $patchInRepo
    } else {
        Move-Item $patchInRepo $patchInTemp
    }
}
if (-not (Test-Path $patchInTemp)) { throw "Patch not found in repository root or TEMP." }

$actualPatchSha256 = (Get-FileHash $patchInTemp -Algorithm SHA256).Hash.ToLowerInvariant()
Write-Host "Patch SHA-256: $actualPatchSha256" -ForegroundColor Cyan

if ((git status --porcelain).Length -ne 0) {
    git status --short
    throw "Working tree must be clean before applying the patch."
}

git fetch origin --prune --tags
if ($LASTEXITCODE -ne 0) { throw "Unable to fetch origin." }
git switch main
if ($LASTEXITCODE -ne 0) { throw "Unable to switch to main." }
git pull --ff-only origin main
if ($LASTEXITCODE -ne 0) { throw "Unable to fast-forward main." }

$expectedBase = "e8f33bb7c0e92d4c49724dadde55d2378cbfddce"
$localHead = (git rev-parse HEAD).Trim()
$remoteHead = (git rev-parse origin/main).Trim()
if ($localHead -ne $expectedBase -or $remoteHead -ne $expectedBase) {
    throw "Baseline mismatch. Expected=$expectedBase Local=$localHead Origin=$remoteHead. Stop and re-audit instead of forcing the patch."
}

$newPath = "docs/acceptance/S0.9-vps-first-hardening.md"
if (Test-Path $newPath) { throw "Acceptance document already exists; inspect repository state before applying twice." }

git apply --check --whitespace=error-all $patchInTemp
if ($LASTEXITCODE -ne 0) { throw "Patch preflight failed." }
git apply --whitespace=error-all $patchInTemp
if ($LASTEXITCODE -ne 0) { throw "Patch apply failed." }
git diff --check
if ($LASTEXITCODE -ne 0) { throw "Whitespace validation failed after patch apply." }

git status --short
git diff --stat
```

This patch tightens first-install recovery, validates the runtime `.env` permissions/ignore state, makes Caddy rollback recovery safer, verifies the single River worker startup, adds CI configuration gates, and blocks GHCR publishing unless the tag commit belongs to `main` and has a successful push CI run for the exact SHA.

For the exact pushed commit, require all of these jobs/steps to pass:

### 3.4 Publish commit-addressed GHCR images

Only after the exact `main` commit is green, create a unique release tag. Check that the tag does not already exist before choosing the version; do not move or overwrite an existing tag.

```powershell
$release = "flowlesshub-v0.1.0" # Increase to the next unused release name when this tag already exists.
git fetch origin --prune --tags
git switch main
git pull --ff-only origin main
$releaseCommit = (git rev-parse HEAD).Trim()
$remoteMain = (git rev-parse origin/main).Trim()
if ($releaseCommit -ne $remoteMain) { throw "Release must tag the current origin/main commit." }
if (@(git tag -l $release).Count -gt 0) { throw "Release tag already exists; choose a new version." }

git tag -a $release $releaseCommit -m "FlowlessHub VPS release $release"
if ($LASTEXITCODE -ne 0) { throw "Unable to create release tag." }
git push origin $release
if ($LASTEXITCODE -ne 0) { throw "Unable to push release tag." }
```

The `verify-release` job in `.github/workflows/publish-images.yml` independently checks that the tag commit is reachable from `origin/main` and that GitHub Actions reports a successful `push` CI run for that exact SHA. Only then does the four-image matrix publish:

- `ghcr.io/weexdayend/flowlesshub-web`
- `ghcr.io/weexdayend/flowlesshub-api`
- `ghcr.io/weexdayend/flowlesshub-worker`
- `ghcr.io/weexdayend/flowlesshub-migrate`

Each image receives both the immutable `sha-<40-character-commit>` tag and the release tag. The workflow builds `linux/amd64` and `linux/arm64`; the web image gets `NEXT_PUBLIC_API_BASE_URL=https://api.flowlesshub.com` as a public build argument. GitHub Actions is the only image-build environment; the VPS performs pulls only.

Wait for `verify-release` and all four image matrix jobs to complete successfully before touching the VPS. Set the four GHCR packages to Public if anonymous pulls are desired. Otherwise authenticate the VPS with a token limited to `read:packages`; never place that token in the repository or `.vps-runtime/.env`.

### 3.5 VPS is the integration/runtime gate

After successful CI and image publication, connect to the VPS and follow Sections 4–12 in order. The candidate must pass direct container-network probes, Caddy loopback probes, public HTTPS probes after Nginx setup, worker startup verification, and resource checks. Traffic switches only after candidate health passes and the memory guard allows it. The previous color remains available for rollback.

A failed VPS runtime check is a deployment failure even when CI is green. Do not mark runtime or production acceptance complete until the actual VPS check passes.

## 6. Validate and perform the first single-color deployment

Run the read-only/config preflight:

```bash
./scripts/vps/preflight.sh
```

Then start FlowlessHub using the dedicated Compose file:

```bash
./scripts/vps/deploy-initial.sh
```

The script performs these actions in order:

1. Confirms Docker/Compose, Nginx, disk/RAM, and verifies that loopback ports 3032/5052 are free or already owned by the FlowlessHub edge during a controlled resume.
2. Validates Compose config.
3. Pulls FlowlessHub release images and pinned infrastructure images.
4. Starts only the FlowlessHub PostgreSQL/PgBouncer services.
5. Waits for the database to become ready.
6. Runs the one-shot migration image against FlowlessHub PostgreSQL.
7. Starts blue API/web, exactly one worker, and Caddy.
8. Verifies exactly one running worker and observes the River worker startup log.
9. Probes API `/readyz` and web `/` from the private Compose network.
10. Validates Caddy and probes Web on 127.0.0.1:3032 and API on 127.0.0.1:5052.
11. Records `blue` as the active color using an atomic state-file replacement.

If a first-install attempt stops partway through, rerun only after inspecting `docker compose ps` and logs. The installer can resume the dedicated FlowlessHub project without deleting containers or volumes; it refuses to overwrite an unexpected runtime Caddyfile. Nginx is still untouched.

## 7. Add Nginx routing without touching existing sites

Nginx is already active and owns ports 80/443. Keep every existing Frictiona/Petshop configuration and upstream unchanged. Add one new site only.

### 7.1 Bootstrap HTTP challenge site

Confirm DNS first, then create the webroot and temporary HTTP-only server:

```bash
sudo install -d -m 0755 /var/www/letsencrypt
if [ -e /etc/nginx/sites-available/flowlesshub ] || [ -L /etc/nginx/sites-enabled/flowlesshub ]; then
  echo "A FlowlessHub Nginx site already exists; inspect/back it up before continuing."
  exit 1
fi
sudo tee /etc/nginx/sites-available/flowlesshub >/dev/null <<'NGINX'
server {
    listen 80;
    listen [::]:80;
    server_name flowlesshub.com app.flowlesshub.com api.flowlesshub.com;
    location ^~ /.well-known/acme-challenge/ {
        root /var/www/letsencrypt;
        default_type text/plain;
        try_files $uri =404;
    }
    location / { return 404; }
}
NGINX
test ! -e /etc/nginx/sites-enabled/flowlesshub && test ! -L /etc/nginx/sites-enabled/flowlesshub
sudo ln -s /etc/nginx/sites-available/flowlesshub /etc/nginx/sites-enabled/flowlesshub
sudo nginx -t
sudo systemctl reload nginx
```

This creates a new named virtual host; it does not edit the existing default or Petshop/Frictiona site files.

### 7.2 Issue the TLS certificate

Install/verify Certbot if not already present. On Ubuntu 24.04, the apt package is sufficient for webroot mode:

```bash
sudo apt-get update
sudo apt-get install -y certbot
sudo certbot certonly --webroot -w /var/www/letsencrypt -d flowlesshub.com -d app.flowlesshub.com -d api.flowlesshub.com
```

Confirm the certificate files exist:

```bash
sudo test -s /etc/letsencrypt/live/flowlesshub.com/fullchain.pem
sudo test -s /etc/letsencrypt/live/flowlesshub.com/privkey.pem
```

Install a deploy hook so renewed certificates are loaded by Nginx without restarting the service:

```bash
sudo install -d -m 0755 /etc/letsencrypt/renewal-hooks/deploy
sudo tee /etc/letsencrypt/renewal-hooks/deploy/flowlesshub-reload-nginx.sh >/dev/null <<'HOOK'
#!/bin/sh
/usr/bin/systemctl reload nginx
HOOK
sudo chmod 0755 /etc/letsencrypt/renewal-hooks/deploy/flowlesshub-reload-nginx.sh
sudo systemctl list-timers --all | grep -i certbot || true
```

If issuance fails, check A/AAAA records and external port 80 reachability. Do not alter other Nginx virtual hosts to work around a DNS issue.

### 7.3 Install the final Nginx virtual host

The repository file `deploy/vps/nginx/flowlesshub.conf` contains the final HTTP redirect, ACME webroot, TLS certificate paths, WebSocket headers, forwarded headers, and private Web/API upstreams `127.0.0.1:3032` and `127.0.0.1:5052`.

## 8. Routine release and blue-green switch

Do not build on the VPS. Every release must have four successful GHCR images and a release SHA tag.

### 8.1 Prepare release on Windows

After source changes pass CI, create/push a new tag using the exact commit SHA, for example `flowlesshub-v0.1.1`. Wait for all four publish jobs to succeed. Record the generated `sha-<40-char-SHA>` tag.

### 8.2 Fetch source and update inactive color on VPS

On VPS:

```bash
cd /opt/flowlesshub
git fetch --prune origin --tags
git checkout --detach flowlesshub-v0.1.1
git rev-parse HEAD
```

Confirm the release SHA equals the commit-addressed GHCR tag. Determine active color:

```bash
cat .vps-runtime/active-color
```

If active is blue, candidate must be green; if active is green, candidate must be blue. Set the candidate image references (this creates a mode-600 `.env` backup and does not restart any service):

```bash
./scripts/vps/set-release.sh green sha-FULL_40_CHARACTER_COMMIT_SHA
```

Replace `green` with the inactive color as appropriate. The script refuses to update the active color. It takes the FlowlessHub deployment lock, creates a protected `.env` backup, writes the new references to a temporary file, validates the candidate Compose configuration, and atomically replaces `.env` only on success. It updates only the inactive color, worker, and migration release references; the currently active color keeps its previous commit-addressed SHA tag for rollback.

### 8.3 Back up and migrate before application switch

Create and validate a FlowlessHub database dump:

```bash
./scripts/vps/backup-db.sh
```

Copy the backup off-host before applying production migrations. Then pull/run the one-shot migration image:

```bash
docker compose --env-file .vps-runtime/.env -f deploy/compose/vps.compose.yaml pull migrate
docker compose --env-file .vps-runtime/.env -f deploy/compose/vps.compose.yaml --profile tools run --rm migrate
```

Migrations must follow expand/contract compatibility. An application rollback does not automatically roll back the database schema. Never restore a database backup as an ordinary application rollback.

### 8.4 Candidate validation and traffic switch

Use the inactive color determined above:

```bash
./scripts/vps/switch-color.sh green
```

The script:

- checks `MemAvailable` before starting the candidate;
- pulls and starts only candidate API/web;
- probes candidate API `/readyz` and web `/` directly on the private Docker network;
- checks post-start memory headroom;
- validates the candidate Caddyfile;
- reloads Caddy through its local admin API (no host Nginx reload required);
- checks the Web and API loopback routes;
- updates active-color state only after success using an atomic file replacement;
- leaves the old color running for rollback; on candidate failure it stops only the inactive target to release memory, never the active color;
- automatically restores and reloads the previous Caddy config if validation, reload, routing probes, or state commit fail. A backup is retained if automatic restoration/reload cannot be confirmed.

If any pre-switch check fails, the active color stays selected. Do not stop it. Inspect the candidate logs and memory use.

### 8.5 Update the single worker

After the web/API traffic switch:

```bash
./scripts/vps/update-worker.sh
```

The script checks that exactly one worker container is running and that its logs contain the River startup message. There must be exactly one FlowlessHub worker. The current worker logs report `business_handlers_registered=false`; it starts River but does not yet process business handlers. Do not scale it or start a second worker as part of this slice.

```bash
curl -fsS https://flowlesshub.com/ >/dev/null
```

Keep the previous color available during the observation window. To conserve RAM after acceptance, stop only its API/web services; do not remove their containers/images or the database volume:

```bash
docker compose --env-file .vps-runtime/.env -f deploy/compose/vps.compose.yaml stop api-blue web-blue
```

Substitute the inactive/old color. This preserves its pinned containers so `switch-color.sh` can restart them during rollback.

## 9. Rollback

### 9.1 Application rollback

Read active color:

```bash
cat .vps-runtime/active-color
```

Run:

```bash
./scripts/vps/rollback-color.sh
```

Use this only after a successful traffic switch. If a candidate switch failed, `active-color` was never changed; keep the current color and inspect candidate logs instead of invoking rollback. Before changing traffic, the script verifies the target color's pinned release and current Compose configuration. It then holds the shared deployment lock across the complete rollback: starts the previously pinned color if it was stopped, validates its API/web health, reloads Caddy to route traffic back, restores the worker image reference to that same release through a protected atomic `.env` replacement, and updates/verifies the single worker. The child scripts verify and reuse the inherited lock descriptor so another release cannot interleave between Web/API and worker rollback. It does not roll back database schema migrations.

If Web/API routing rollback succeeds but the worker cannot start, the `.env` remains pinned to the rollback release. Diagnose worker logs and rerun `./scripts/vps/update-worker.sh`; do not rerun `rollback-color.sh`, because the traffic color has already changed. The rollback script holds the shared deployment lock through the worker update so another release cannot interleave between the two steps.

Application rollback is safe only when the new migration is backward-compatible with the previous application. This is why migrations must be expand/contract.

### 9.2 Nginx rollback

If Nginx config validation fails before reload, do not reload. Restore only `/etc/nginx/sites-available/flowlesshub` from the saved copy and run `sudo nginx -t`. Existing Petshop/Frictiona Nginx files must not be touched.

### 9.3 Database recovery

Database restore is a disaster-recovery operation, not the standard release rollback. Confirm the exact FlowlessHub volume/database and coordinate downtime before restore. Never restore a FlowlessHub dump into `petshop-postgres`.

## 10. Backup and monitoring

Create backup:

```bash
./scripts/vps/backup-db.sh
```

Backups are mode 600 under `.vps-runtime/backups`. Copy them off-host to approved durable storage and periodically test restore in a separate disposable database. For example, from a trusted Windows workstation (replace the host/IP and exact filename):

```powershell
New-Item -ItemType Directory -Force .\flowlesshub-backups | Out-Null
scp ubuntu@YOUR_VPS_HOST:/opt/flowlesshub/.vps-runtime/backups/flowlesshub-YYYYMMDDTHHMMSSZ.dump .\flowlesshub-backups\
```

Store off-host copies encrypted and access-controlled. The Docker named volume alone is not a backup.

Monitor:

```bash
docker stats --no-stream
docker compose --env-file .vps-runtime/.env -f deploy/compose/vps.compose.yaml ps
docker compose --env-file .vps-runtime/.env -f deploy/compose/vps.compose.yaml logs --tail=100 edge api-blue web-blue worker postgres pgbouncer
free -h
swapon --show
df -h /
sudo journalctl -k --since '24 hours ago' | grep -Ei 'oom|out of memory|killed process' || true
```

## 11. Stop/restart policy and forbidden cleanup

Restart only FlowlessHub services if needed:

```bash
docker compose --env-file .vps-runtime/.env -f deploy/compose/vps.compose.yaml restart edge
```

Do not use `docker compose down` as an ordinary deployment command. Do not remove named volumes. Never run global prune commands on this host while Petshop is live. A FlowlessHub-only teardown, if ever explicitly approved, must name the exact Compose file/project and preserve `flowlesshub-vps-postgres-data` unless a separately reviewed data-destruction plan exists.
