# FlowlessHub VPS Deployment Runbook — Ubuntu + Docker Compose + Nginx/Caddy Blue-Green

**Target host:** Ubuntu 24.04 LTS, existing host Nginx, Docker Engine + Compose plugin
**Domains:** `flowlesshub.com`, `app.flowlesshub.com`, `api.flowlesshub.com`
**Registry:** GHCR (`ghcr.io/weexdayend`)
**Application ports:** API container `5050`, Web container `3000`
**Private edge:** Web upstream `127.0.0.1:3032`; API upstream `127.0.0.1:5052`
**Existing Petshop ports:** web `3031`, API `5051`, PostgreSQL `5433`, Redis `6380`, Adminer `8080`
**Verified source baseline:** `main` at `ae3d03fd8736b3afc60aec50ff5b5a0c6662f808` (`fix(S0.8): make edge validation portable`)
**Baseline CI:** GitHub Actions run [#25](https://github.com/weexdayend/flowlesshub/actions/runs/43133943125) — passed on that exact commit
**Runbook refresh:** 2026-11-12

## 0. Safety contract

This deployment is deliberately isolated from the existing Petshop Compose project and containers.

- Do not change, recreate, stop, rename, or remove `petshop-web`, `erp-petshop-api-1`, `petshop-postgres`, `petshop-redis`, or `petshop-adminer`.
- Do not attach FlowlessHub to the `petshop-internal` network or use the Petshop PostgreSQL/Redis volumes.
- Do not use host networking. Do not publish FlowlessHub PostgreSQL/PgBouncer ports.
- Do not run broad `docker compose down`, `docker system prune`, `docker volume prune`, or `docker image prune` as part of this runbook.
- Never use `docker compose down -v` for FlowlessHub. The PostgreSQL volume is persistent data.
- Nginx remains the only public listener on host ports 80/443. Caddy binds only `127.0.0.1:3032` (web) and `127.0.0.1:5052` (API); it has no public TLS listener.
- All commands are project-scoped to `deploy/compose/vps.compose.yaml` and a dedicated Compose project/network/volume.
- Run the deployment as the normal Docker operator (`ubuntu` in the supplied host output). Use `sudo` only for host Nginx/Certbot/system inspection.

The current API implementation exposes `/livez` and `/readyz`. It does not yet expose business endpoints or a CORS policy. The API hostname is configured now for future use and health validation; this deployment does not claim that a complete business API already exists. Before browser code at `flowlesshub.com` or `app.flowlesshub.com` calls cross-origin business endpoints at `api.flowlesshub.com`, add an explicit CORS allowlist for those two HTTPS origins (or adopt a same-origin API path). The frontend currently renders the foundation workspace; it does not yet prove end-to-end business workflows.

## 1. Architecture

```text
Internet
  |
  +-- flowlesshub.com / app.flowlesshub.com / api.flowlesshub.com
  |
Host Nginx :80/:443  (existing service, owns TLS)
  |
  +-- flowlesshub.com / app.flowlesshub.com -> 127.0.0.1:3032
  |       Caddy :3032 -> active web color :3000
  |
  +-- api.flowlesshub.com -> 127.0.0.1:5052
          Caddy :5052 -> active API color :5050

Blue/green candidates live on the private Compose edge network.

Private backend network:
  API -> PgBouncer:6432 -> FlowlessHub PostgreSQL:5432
  Worker -> PostgreSQL:5432 (direct session connection)
  Migration -> PostgreSQL:5432 (direct session connection)
```

FlowlessHub has its own `flowlesshub-vps` Compose project, `flowlesshub-vps-edge` and `flowlesshub-vps-backend` networks, `flowlesshub-vps-postgres-data` volume, and Web cache volumes. The backend network is internal. No FlowlessHub database port is published to the host or Internet.

Nginx routes the two web hostnames to Caddy :3032 and the API hostname to Caddy :5052. Caddy switches Web and API together to the same active color using one validated config. This keeps existing Frictiona/Petshop Nginx server blocks unchanged while retaining a Caddy-controlled blue-green switch.

## 2. Capacity policy for the current 2 GiB VPS

The host snapshot showed approximately 100 MiB combined Petshop container usage at that instant and approximately 29 GiB free disk. An earlier `free -h` snapshot showed around 591 MiB available RAM; this must be measured again immediately before deployment. Docker reported 7.779 GiB BuildKit cache, but this runbook does not prune it.

The Compose resource ceilings are intentionally constrained (PostgreSQL 384 MiB, PgBouncer 64 MiB, each API 96 MiB, each Web 256 MiB, worker 96 MiB, Caddy 64 MiB). These are ceilings, not guaranteed real usage or a RAM reservation.

- Initial single-color deployment refuses to proceed below 256 MiB `MemAvailable`.
- Starting a stopped blue-green candidate requires `FLOWLESSHUB_MIN_AVAILABLE_MIB` (default 384 MiB) before starting the inactive color. Reusing an already-running inactive color skips this additional-start guard because it does not add another API/Web pair.
- After candidate startup/reuse, traffic switching is refused if `MemAvailable` falls below 256 MiB. Only the inactive candidate is stopped; the active color remains running.
- If the guard refuses a blue-green overlap, do not lower the threshold just to force deployment. Upgrade RAM or reduce unrelated host workloads after an explicit review.
- A 2 GiB VPS is a constrained first-production target. Monitor `docker stats`, `/proc/meminfo`, swap, and OOM logs. Do not promise zero-downtime blue-green under memory pressure.

## 7. Add Nginx routing without touching existing sites

Nginx is already active and owns ports 80/443. Keep every existing Frictiona/Petshop configuration and upstream unchanged. Add one new site only.

### 7.1 Bootstrap HTTP challenge site

Confirm DNS first, then create the webroot and temporary HTTP-only server:

```bash
sudo install -d -m 0755 /var/www/letsencrypt
if [ -e /etc/nginx/sites-available/flowlesshub ] || [ -L /etc/nginx/sites-enabled/flowlesshub ]; then
  echo "A FlowlessHub Nginx site already exists; inspect/back it up before continuing."
  exit 1
fi
sudo tee /etc/nginx/sites-available/flowlesshub >/dev/null <<'NGINX'
server {
    listen 80;
    listen [::]:80;
    server_name flowlesshub.com app.flowlesshub.com api.flowlesshub.com;
    location ^~ /.well-known/acme-challenge/ {
        root /var/www/letsencrypt;
        default_type text/plain;
        try_files $uri =404;
    }
    location / { return 404; }
}
NGINX
test ! -e /etc/nginx/sites-enabled/flowlesshub && test ! -L /etc/nginx/sites-enabled/flowlesshub
sudo ln -s /etc/nginx/sites-available/flowlesshub /etc/nginx/sites-enabled/flowlesshub
sudo nginx -t
sudo systemctl reload nginx
```

This creates a new named virtual host; it does not edit the existing default or Petshop/Frictiona site files.

### 7.2 Issue the TLS certificate

Install/verify Certbot if not already present. On Ubuntu 24.04, the apt package is sufficient for webroot mode:

```bash
sudo apt-get update
sudo apt-get install -y certbot
sudo certbot certonly --webroot -w /var/www/letsencrypt -d flowlesshub.com -d app.flowlesshub.com -d api.flowlesshub.com
```

Confirm the certificate files exist:

```bash
sudo test -s /etc/letsencrypt/live/flowlesshub.com/fullchain.pem
sudo test -s /etc/letsencrypt/live/flowlesshub.com/privkey.pem
```

Install a deploy hook so renewed certificates are loaded by Nginx without restarting the service:

```bash
sudo install -d -m 0755 /etc/letsencrypt/renewal-hooks/deploy
sudo tee /etc/letsencrypt/renewal-hooks/deploy/flowlesshub-reload-nginx.sh >/dev/null <<'HOOK'
#!/bin/sh
/usr/bin/systemctl reload nginx
HOOK
sudo chmod 0755 /etc/letsencrypt/renewal-hooks/deploy/flowlesshub-reload-nginx.sh
sudo systemctl list-timers --all | grep -i certbot || true
```

If issuance fails, check A/AAAA records and external port 80 reachability. Do not alter other Nginx virtual hosts to work around a DNS issue.

### 7.3 Install the final Nginx virtual host

The repository file `deploy/vps/nginx/flowlesshub.conf` contains the final HTTP redirect, ACME webroot, TLS certificate paths, WebSocket headers, forwarded headers, and private Web/API upstreams `127.0.0.1:3032` and `127.0.0.1:5052`.

If `nginx -t` fails, do not reload. Restore only the new FlowlessHub file with `sudo cp -a /etc/nginx/sites-available/flowlesshub.http-bootstrap.bak /etc/nginx/sites-available/flowlesshub`, rerun `sudo nginx -t`, and reload only after it passes. Existing site files must remain untouched.

### 8.3 Back up and migrate before application switch

Create and validate a FlowlessHub database dump:

### 8.4 Candidate validation and traffic switch

Use the inactive color determined above:

```bash
./scripts/vps/switch-color.sh green
```

The script:

- checks `MemAvailable` before starting the candidate;
- pulls and starts only candidate API/web;
- probes candidate API `/readyz` and web `/` directly on the private Docker network;
- checks post-start memory headroom;
- validates the candidate Caddyfile;
- reloads Caddy through its local admin API (no host Nginx reload required);
- checks the Web and API loopback routes;
- updates active-color state only after success;
- leaves the old color running for rollback; on candidate failure it stops only the inactive target to release memory, never the active color.

If any pre-switch check fails, the active color stays selected. Do not stop it. Inspect the candidate logs and memory use.

### 8.5 Update the single worker

After the web/API traffic switch:

```bash
./scripts/vps/update-worker.sh
```

There must be exactly one FlowlessHub worker. The current worker logs report `business_handlers_registered=false`; it starts River but does not yet process business handlers. Do not scale it or start a second worker as part of this slice.

### 8.6 Observe, then release standby resources

## 9. Rollback

### 9.1 Application rollback

Read active color:

```bash
cat .vps-runtime/active-color
```

Run:

```bash
./scripts/vps/rollback-color.sh
```

Use this only after a successful traffic switch. If a candidate switch failed, `active-color` was never changed; keep the current color and inspect candidate logs instead of invoking rollback. After a successful switch, the script starts the previously pinned color if it was stopped, validates its API/web health, reloads Caddy to route traffic back, restores the worker image reference to that same release, and updates the single worker. It does not roll back database schema migrations.

Application rollback is safe only when the new migration is backward-compatible with the previous application. This is why migrations must be expand/contract.

### 9.2 Nginx rollback

If Nginx config validation fails before reload, do not reload. Restore only `/etc/nginx/sites-available/flowlesshub` from the saved copy and run `sudo nginx -t`. Existing Petshop/Frictiona Nginx files must not be touched.

### 9.3 Database recovery

Database restore is a disaster-recovery operation, not the standard release rollback. Confirm the exact FlowlessHub volume/database and coordinate downtime before restore. Never restore a FlowlessHub dump into `petshop-postgres`.

## 11. Stop/restart policy and forbidden cleanup
