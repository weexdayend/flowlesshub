# S0.11 — Scheduled Backup Operations, Retention & Off-Site Recovery

**Status:** `PREPARED`; owner policy decisions, Windows application/review, exact-SHA CI, and VPS runtime acceptance pending.
**Patch base:** `94536d65317aa513bdc715a39fbce2789dbb8709`
**Production activation:** Not performed. The systemd timer is not installed/enabled; off-site upload and deletion defaults are disabled.

## 1. Goal

Move FlowlessHub from the S0.10 one-time, owner-executed backup/restore proof to an operationally repeatable backup workflow while preserving the 2 GiB VPS resource limits and strict isolation from Petshop/Frictiona. Provide scheduling artifacts, local retention controls, provider-neutral encrypted off-site upload support, and a safe runbook without silently making unresolved policy choices.

## 2. Current facts and constraints inherited from S0.10

- Accepted S0.10 source SHA: `94536d65317aa513bdc715a39fbce2789dbb8709`.
- Existing backup script: `scripts/vps/backup-db.sh`.
- Existing verifier: `scripts/vps/verify-backup.sh`.
- Existing isolated restore: `scripts/vps/restore-drill.sh`.
- All three use `.vps-runtime/backup.lock` for backup/restore serialization.
- The database is PostgreSQL 17.11 in Compose project `flowlesshub-vps`.
- Backups are a `.dump`, `.sha256`, `.manifest` triplet under `.vps-runtime/backups`, mode 0600; directory mode 0700.
- Current scripts already guard memory, swap, disk, PostgreSQL health, active-color marker, and ignored/mode-600 `.env`.
- The observed S0.10 pre-restore snapshot was ~560 MiB MemAvailable, ~1.05 GiB SwapFree, and ~28 GB disk free. This is historical evidence, not a live guarantee.
- Off-host Windows checksum verification exists, but geographic/cloud off-site storage does not.
- No backup cadence, retention count, S3-compatible provider, bucket, region, cloud credentials, alert destination, recurring restore cadence, RPO, or RTO has been selected.

## 3. Proposed architecture

```text
systemd timer (proposed daily schedule; disabled until approval)
  -> flowlesshub-backup.service (oneshot, journald output)
     -> scripts/vps/scheduled-backup.sh
        -> scripts/vps/backup-db.sh
           -> PostgreSQL custom dump + SHA256 + manifest
           -> shared .vps-runtime/backup.lock
        -> scripts/vps/offsite-backup.sh (only when enabled/configured)
           -> Restic S3-compatible encrypted repository
           -> exact snapshot selection + archive-triplet read-back + local upload marker
        -> scripts/vps/backup-retention.sh
           -> dry-run by default
           -> live remote snapshot check before local deletion
```

The systemd service itself does not deploy or restart application services. No application image changes are required. The existing Docker Compose project remains unchanged.

## 4. Implementation package

### `scripts/vps/scheduled-backup.sh`

- Orchestrates the existing verified local backup, optional off-site upload, and local retention review.
- Captures the exact archive path from the existing backup script output; accepts repeated identical `Archive:` lines from the backup/verifier output but rejects missing or multiple distinct archive paths.
- Treats exit code 3 from the off-site script as `disabled/not configured`, retaining the local backup. Any other off-site error stops before retention.
- Runs retention dry-run by default. Automatic deletion requires a protected retention policy with `FLOWLESSHUB_BACKUP_RETENTION_AUTO_PRUNE=1`, in addition to the deletion policy's own explicit guards.
- Writes no credentials or secret values to logs.

### `scripts/vps/offsite-backup.sh`

- Uses Restic with an S3-compatible HTTPS repository (`s3:https://...`) as a provider-neutral backend. No provider or bucket is selected in this package.
- Requires owner-controlled `.vps-runtime/offsite.env`, mode 0600, owned by the executing account; off-site must be explicitly enabled.
- Requires a separate Restic password file under `.vps-runtime`, mode 0600 and owned by the executing account. Off-site upload and retention canonicalize the configured path with `realpath -e` and reject a resolved path outside the canonical runtime directory. Restic repository encryption is only useful if this password is backed up securely outside the VPS.
- Requires repository to have been initialized separately. The automation never runs `restic init` and never creates/reinitializes a remote repository silently.
- Verifies archive, sidecars, manifest, and checksum before upload.
- Uses the shared `.vps-runtime/backup.lock`, uploads the archive triplet, lists the matching tagged snapshot, then uses `restic dump` to read all three files back from that exact snapshot and compare their SHA-256 hashes with the local files before writing a protected `.offsite-uploaded` marker.
- The versioned marker records the archive, sidecar, and manifest read-back SHA-256 values, read-back scope, exact snapshot ID, and upload time. It proves those three files were readable and byte-matched at upload time; it is not a PostgreSQL restore drill or a full repository integrity audit.

### `scripts/vps/backup-retention.sh`

- Dry-run is the default. No file is deleted without `--apply`.
- Requires a protected retention policy, explicit `FLOWLESSHUB_BACKUP_RETENTION_ENABLED=1`, a numeric keep count of at least 2, and `FLOWLESSHUB_BACKUP_RETENTION_ALLOW_DELETE=1` for apply.
- Validates every local archive triplet, mode, manifest identity, checksum, and versioned off-site marker, including all three recorded read-back hashes.
- For every deletion candidate, performs a live Restic snapshot lookup and confirms the exact snapshot ID/tag is still present. In `--apply` mode it also reads the archive, checksum sidecar, and manifest back from that snapshot again and compares SHA-256 values immediately before deletion. A marker or snapshot listing alone is insufficient.
- Keeps the newest configured number of backups. It only considers older archive groups that have matching off-site marker and live remote snapshot evidence; actual deletion additionally requires fresh remote byte read-back.
- It does not prune remote Restic snapshots. Remote retention/pruning is deliberately a separate policy/approval.
- Serializes with backup/upload/restore using `.vps-runtime/backup.lock`.

### systemd artifacts

- `deploy/systemd/flowlesshub-backup.service`: oneshot service, fixed working directory, dedicated `ubuntu` user, restrictive filesystem/kernel settings, `UMask=0077`, resource-friendly scheduling priority, long operation timeout, and write access limited to `.vps-runtime`. Restic's cache is explicitly redirected to the service's private `/tmp` because `ProtectHome=true` hides `/home/ubuntu`.
- `deploy/systemd/flowlesshub-backup.timer`: proposed daily `03:00 UTC` schedule with up to 15 minutes randomized delay and `Persistent=true` catch-up behavior. It is not installed or enabled by this package.
- The service requires the execution account to have Docker socket access. Confirm the `ubuntu` account's Docker group membership before installation; do not add permissions silently.
- Until an external alert destination is selected, service success/failure is visible through systemd result and journald only.

### Protected config templates

- `deploy/vps/offsite.env.example` — repository endpoint and credential variable names; contains placeholders only.
- `deploy/vps/backup-retention.env.example` — disabled-by-default retention controls; contains no secrets.
- Actual runtime files belong only under `.vps-runtime/`, which is Git-ignored. Never commit populated copies.

## 5. Fail-closed defaults

- Timer: not installed, not enabled, not started.
- Off-site: `FLOWLESSHUB_OFFSITE_ENABLED=0`; no repository, bucket, keys, or Restic password provisioned.
- Retention: `FLOWLESSHUB_BACKUP_RETENTION_ENABLED=0`; `KEEP_LAST` unset; deletion `ALLOW_DELETE=0`; auto-prune `AUTO_PRUNE=0`.
- No remote repository initialization.
- No remote `forget`/`prune`.
- No automatic restore drill.
- No external alert integration.
- No RPO/RTO numbers.
- No RAM/swap/disk guard reduction.

## 6. Proposed schedule (owner approval required)

The candidate timer is daily at `03:00 UTC`, with up to 15 minutes of randomized delay and `Persistent=true`. Jakarta is UTC+7, so 03:00 UTC corresponds to 10:00 WIB. This is a proposal only; no timer installation or activation is included in S0.11 preparation. With `Persistent=true`, enabling the timer after a missed activation window may run a catch-up operation; the operator must inspect service state and local resources before enabling it.

## 8. Acceptance boundaries

CI can verify Bash syntax, ShellCheck, executable mode, and static configuration only. VPS runtime acceptance must independently prove a scheduled service run, output artifacts and checksums, resource guards, off-site upload/list/read-back (only after provider selection), retention dry-run and a separately approved controlled deletion, journald failure visibility, and preservation of production/Petshop resources.

Do not call S0.11 closed merely because the timer unit parses or a Restic snapshot can be listed. A marker is not a restore drill. Do not infer RPO from schedule alone, and do not infer service RTO from `pg_restore` duration.

## 9. Out of scope

- Selecting or purchasing cloud storage.
- Generating or storing real credentials in source control.
- Automatically initializing a remote repository.
- Automatic remote snapshot prune.
- Automatic production restore or scheduled restore drill.
- External monitoring/notification integration.
- Changing Compose services, application images, database schema, Nginx, active color, or Petshop/Frictiona infrastructure.
- Any application restart or release deployment.
