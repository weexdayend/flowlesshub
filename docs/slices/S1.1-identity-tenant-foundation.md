## 1. Outcome

Deliver the backend/API identity foundation: the first organization owner can be provisioned, credentials can be authenticated through the internal identity API, sessions are revocable, and authenticated API clients can identify only organizations for which the user has active membership. The foundation supports a user belonging to more than one organization without permitting client-supplied tenant identifiers to bypass membership checks.

S1.1 does not deliver browser sign-in/session UX or protected Next.js application routes. The web UX is an explicit owner-approved deferral to the first workstream in S1.2; this is not an unreported implementation omission.

This is a backend-first vertical slice. It does not make the product launch-ready by itself; the MVP is the ordered Lead-to-Quotation workflow in `docs/roadmap/S1-MVP-ROADMAP.md`.

## 3. Domain decisions

### 3.1 Identity is global; organization is the tenant boundary

- One `identity.users` record represents one human identity across FlowlessHub.
- Email is normalized using trim + lowercase for uniqueness. Do not apply provider-specific transformations such as Gmail dot removal or plus-address stripping.
- A user may have memberships in multiple `tenant.organizations` records.
- An organization is the initial tenant boundary for every future customer, lead, survey, RAB, quotation, project, and finance record. Each tenant-owned business record must carry a non-null `organization_id`.
- Do not add a second generic `workspace` layer in S1.1. Add one only when a concrete product requirement establishes a separate billing/security boundary.

### 3.2 Core relational model

Create PostgreSQL schemas `identity` and `tenant` through additive Goose migrations. UUID primary keys and explicit foreign keys are mandatory.

| Relation | Required responsibility and invariants |
|---|---|
| `identity.users` | Global account; normalized unique email; display name; versioned password hash; `active` / `disabled` status; timestamps. Never persist plaintext passwords. |
| `tenant.organizations` | Tenant identity; unique normalized slug; display/legal name; `active` / `suspended` status; timestamps. |
| `tenant.memberships` | Unique `(organization_id, user_id)` membership; role `owner`, `admin`, or `member`; status `active`, `invited`, or `suspended`; timestamps. |
| `identity.sessions` | User FK; unique 32-byte SHA-256 digest of a cryptographically random 256-bit token; creation, expiry, last-use, and revocation timestamps. Raw session tokens must never be stored. |
| `identity.auth_events` | Minimal security audit event (login success/failure, logout/revocation, bootstrap). Never store passwords, raw tokens, cookie values, or webhook/connection credentials. |

The database enforces uniqueness, foreign keys, status/role check constraints, non-empty normalized identifiers, and useful indexes for email lookup, active memberships, and unrevoked/unexpired sessions. S1.1 exposes no membership mutation endpoint, so final-active-owner mutation protection is a mandatory S1.2 gate before owner removal, suspension, or demotion is introduced. S1.2 must enforce and test the invariant transactionally under concurrent membership changes.

Use PostgreSQL `TIMESTAMPTZ` for instants and store timestamps in UTC. Use `TEXT`/`VARCHAR` with explicit checks instead of depending on optional extensions such as `citext`.

### 3.3 Authentication — internal session issuer

- FlowlessHub owns credential verification and session issuance. Do not add a third-party identity provider as a runtime dependency in S1.1.
- Use opaque, CSPRNG-generated 256-bit session tokens. Persist only a SHA-256 token digest, keyed by a session row; compare digests in constant time where comparison occurs in application code.
- Do not use self-contained JWT access tokens for the first-party browser session. Database-backed opaque sessions provide immediate logout, revocation, account-disable enforcement, and a straightforward single-session inventory.
- Password hashes must use Argon2id with a versioned, parameter-bearing encoded format. Parameters must be centralized, documented, benchmarked on the VPS-equivalent CPU/memory budget, and bounded by an authentication concurrency limit. Passwords must have minimum length, a bounded maximum byte length, and must not be silently trimmed.
- Sessions have a fixed 12-hour absolute lifetime in S1.1. No indefinite sliding extension and no refresh-token family until a measured product requirement justifies them.
- The browser session cookie is host-only for the API host, `HttpOnly`, `Secure` in deployed environments, `SameSite=Lax`, and `Path=/`. Do not set a broad parent-domain cookie and do not expose the session token to JavaScript/localStorage/sessionStorage. Local HTTP development must use an explicitly separate development cookie configuration; production security defaults must fail closed.
- Credential-changing/authentication POST requests must validate the exact configured web Origin. CORS must allow only the configured web origin with credentials; never use wildcard origin with credentialed cookies. Reject untrusted/malformed Origin values. Handle preflight explicitly.
- Login failures must return a generic authentication error that does not reveal whether an email exists, an account is disabled, or a password was incorrect. Do not log credentials or session values.
- Provide logout/revocation and `/me` session introspection. Expired, revoked, or disabled-user sessions are rejected on every authenticated request.

### 3.4 First owner provisioning and onboarding boundary

- S1.1 uses a controlled one-time CLI bootstrap for the first organization owner. It must acquire a PostgreSQL advisory transaction lock, verify that no user/organization has already been provisioned, and create the initial user, organization, and owner membership atomically.
- The bootstrap command must read the password from a no-echo terminal prompt (not from command-line arguments, shell history, or committed environment files). It must never print the password or password hash.
- The bootstrap command must refuse a second invocation once the initial identity exists; it must not offer an override/force flag.
- Public self-service registration is intentionally disabled in S1.1. Do not expose an open signup endpoint until email verification, abuse controls, and a support/recovery path are implemented and accepted.
- Additional users/invitations and organization creation after initial bootstrap are a subsequent slice, not a hidden side effect of the bootstrap command.

## 4. Tenant isolation contract

- A tenant context is derived from the authenticated user plus an organization membership lookup. A request header/query parameter/body field alone never establishes tenant access.
- Every tenant-scoped repository operation must require both `organization_id` and the authorized actor; never fetch a tenant record by its UUID alone and then rely on the frontend to filter it.
- Do not trust an `organization_id` supplied by a browser until the API has confirmed the user has an active membership and the organization is active.
- Before S1.2 introduces the first customer or other business table, add and test transaction-local tenant context (`SET LOCAL` / `set_config(..., true)`), FORCE ROW LEVEL SECURITY as appropriate, and a non-owner application database role. The current foundation connection role owns migration-created tables and must not be treated as proof of RLS isolation. Pool/PgBouncer transaction boundaries must not leak tenant context.
- A cross-tenant negative test is a release blocker before customer data is added. No production migration or data access is authorized by this specification.

## 5. API contract to implement

The exact OpenAPI schemas/operation IDs are to be authored in `api/openapi.yaml` and generated through the repository's existing generators. The initial API surface is:

| Method | Path | Auth | Behavior |
|---|---|---|---|
| `POST` | `/v1/auth/login` | Public, origin-checked | Verify credentials and issue host-only session cookie. |
| `POST` | `/v1/auth/logout` | Session | Revoke current session and expire cookie; idempotent. |
| `GET` | `/v1/auth/me` | Session | Return safe user profile, session expiry, and active organization memberships/roles. |
| `GET` | `/v1/organizations` | Session | Return only organizations for which the authenticated user has an active membership. |

No password-reset, invite acceptance, self-registration, SSO, MFA, API-key, public/vendor/client, or billing endpoint is part of S1.1. No cost/margin values may be added to public/client/vendor response schemas.

## 7. Required tests and acceptance criteria

- Password hash creation/verification, wrong-password rejection, malformed hash rejection, parameter parsing, and concurrency bounds.
- Email normalization and unique identity constraints; duplicate email race returns a safe conflict.
- Bootstrap success, atomic rollback, advisory-lock serialization, and refusal after the first owner exists.
- Session token entropy/format, digest-only persistence, expiry, revocation, disabled-user rejection, and logout idempotency.
- Cookie attributes in production and explicit local-development mode; no raw token in JSON, logs, traces, or error bodies.
- Exact Origin allowlist, credentialed CORS, preflight, and rejected cross-origin state-changing request.
- Generic login failure response; no account enumeration; bounded login abuse controls.
- Active membership listing and suspended membership/organization rejection are S1.1 criteria; final-active-owner protection and concurrent ownership-transfer tests are mandatory S1.2 gates before owner mutation endpoints are exposed.
- Cross-tenant request with a valid user but non-member organization is denied. Before S1.2 business tables are merged, the RLS/non-owner-role proof and PgBouncer transaction-local context tests are mandatory.
- Goose migration up/down and sqlc/OpenAPI generated output are reproducible; no generated drift.
- `go test -race ./...`, `go vet ./...`, Go module tidy, SQL migration lint, architecture lint, full CI, and frontend lint/typecheck/build pass on the exact pushed SHA.
