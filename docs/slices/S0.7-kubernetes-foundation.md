# S0.7 — Kubernetes Deployment Foundation and Container Image Gates

**Status:** Implementation prepared; owner image-build/manifest validation and exact-HEAD CI acceptance pending. S0 remains open.

## Goal

Close the missing Kubernetes-compatible workload-manifest foundation and make every existing application container image build in CI. Preserve the current separate backend/frontend Compose projects and existing Dockerfiles.

## Current baseline

- Frontend image: `apps/web/Dockerfile` (Next.js standalone runtime, non-root UID 1001).
- Backend image: `services/api/Dockerfile`, parameterized by `APP=api|worker|migrate`, distroless non-root runtime.
- Local backend and frontend Compose files exist and remain separate.
- PostgreSQL/PgBouncer configuration and migration ordering are owned by the S0.2 Compose slice.
- OpenAPI Go and TypeScript generated artifacts are already freshness-checked in CI.

## Scope

- Add Kustomize base manifests for the namespace, runtime ConfigMap, API Deployment/ClusterIP Service, web Deployment/ClusterIP Service, and worker Deployment.
- Add a separate one-shot migration Job package. Operators must run and wait for the Job before applying/rolling out API and worker workloads.
- Keep PostgreSQL and PgBouncer external to the production Kubernetes workload package. For Docker Desktop smoke acceptance only, the local helper dynamically creates a separate single-replica in-cluster PostgreSQL/PgBouncer runtime with ephemeral storage; it is not rendered by `deploy/k8s/base` and is never a production topology.
- Consume one Secret named `flowlesshub-runtime-secrets` with three separate keys: `DATABASE_URL_API`, `DATABASE_URL_WORKER`, `DATABASE_URL_MIGRATE`. API uses PgBouncer; worker and migration use direct PostgreSQL connections. The local Docker Desktop smoke test provisions it through `scripts/k8s/provision-local-runtime.ps1`; real clusters use their selected secret manager.
- Apply Restricted Pod Security defaults: non-root UID/GID, RuntimeDefault seccomp, no service-account token mount, no privilege escalation, read-only root filesystem, and all capabilities dropped.
- Use explicit resource requests/limits, API readiness/liveness probes, web HTTP probes, safe rolling update settings for stateless HTTP workloads, and a non-overlapping worker Recreate strategy.
- Mount bounded ephemeral writable directories for Next.js runtime cache and `/tmp`; keep the rest of the web root filesystem read-only.
- Add Makefile targets to build the web/API/worker/migration images and render both Kustomize packages.
- Extend CI to build (but not publish) all four images and validate both Kustomize packages with pinned Kustomize v5.8.3.
- Add the slice spec and complete Windows PowerShell runbook.

## Runtime and rollout contract

1. For Docker Desktop local acceptance, run `scripts/k8s/provision-local-runtime.ps1`; it starts an isolated Compose PostgreSQL/PgBouncer pair, verifies Pod-to-host connectivity, and creates the runtime Secret without writing credential values to disk or Git. For remote/production clusters, provision the same Secret using the selected secret manager.
2. Apply `deploy/k8s/migrations` and wait for `job/flowlesshub-migrate` to complete successfully.
3. Inspect migration logs and preserve the completed Job as deployment evidence.
4. Only then apply `deploy/k8s/base` and wait for API/web/worker rollouts.
5. On a later release, delete the prior completed migration Job before creating a fresh Job; Kubernetes Jobs are immutable and a completed Job does not rerun on `apply`.

The API readiness probe calls `/readyz` and therefore reflects PgBouncer/database reachability. Liveness calls `/livez` and does not depend on PostgreSQL. The worker currently has no HTTP health endpoint; no fake liveness command is added. Its rollout uses `Recreate` so the single worker drains via SIGTERM before replacement, while River handles unfinished-job retry semantics.

## Image and environment policy

- CI builds four local validation tags: `flowlesshub-web:dev`, `flowlesshub-api:dev`, `flowlesshub-worker:dev`, and `flowlesshub-migrate:dev`. CI does not push images or create a registry/package.
- The manifest image names are local-development defaults. A real cluster rollout must replace them with immutable tags in the selected registry. Do not deploy mutable `dev` tags to production.
- `flowlesshub-runtime-secrets` is intentionally not committed. No passwords, real database URLs, Secret manifests, kubeconfigs, cluster credentials, or registry credentials enter Git.
- The frontend's `NEXT_PUBLIC_*` values are build-time inputs in Next.js. This slice does not invent a public API origin or change frontend build-time environment behavior.
- No production ingress, reverse proxy, TLS termination, blue/green traffic switch, HPA, NetworkPolicy, PostgreSQL StatefulSet, or PgBouncer Deployment is introduced. The local helper creates only a disposable smoke-test Deployment/Service using `emptyDir`; it is excluded from production Kustomize packages, is non-durable, and must be deleted during cleanup.

## Security and availability defaults

- Namespace enforces Kubernetes Pod Security `restricted` labels.
- API/web have two replicas and rolling update `maxUnavailable: 0`; they use ClusterIP only and wait for readiness before receiving Service traffic.
- API/worker/migration use the existing distroless non-root image UID 65532.
- Web uses the existing non-root UID 1001; only `.next/cache` and `/tmp` are writable through size-limited `emptyDir` mounts.
- No Kubernetes ServiceAccount token is mounted because these processes do not call the Kubernetes API.
- Migration Job runs once, sequentially, with a bounded active deadline and no parallelism.

## Acceptance

1. Both Kustomize packages render successfully using pinned v5.8.3.
2. Frontend image builds from `apps/web/Dockerfile`.
3. API, worker, and migration images build from `services/api/Dockerfile` with their exact `APP` build arguments.
4. Existing frontend lint/typecheck/build and backend module, vet, test gates remain green.
5. CI checks build all four images and render the base plus migration packages on every push/PR.
6. Rendered manifests contain one namespace, three Deployments, two Services, one migration Job, and no committed Secret data.
7. Owner optionally verifies the migration-before-workload sequence against a disposable Kubernetes cluster and disposable PostgreSQL database. This is not a production deployment or S0 exit-gate claim.
8. Exact-HEAD frontend and backend CI jobs pass.

## Non-goals

- No image push, signing, SBOM, Trivy scan, registry selection, or deploy workflow; these remain separate CI/CD/security slices.
- No claim of production deployment, blue/green rollout, edge TLS, or rollback rehearsal.
- No S0 checklist box or S0 exit gate is marked complete by this implementation slice.
