# S0.7 — Kubernetes Deployment Foundation and Container Image Gates

**Status:** Local Kubernetes smoke acceptance and exact-HEAD CI acceptance passed. The legacy Compose-project cleanup is not independently verified in this record. S0 remains open.

## Goal

Provide Kubernetes-compatible workload manifests and make every existing application container image build in CI, while preserving the separate backend/frontend Compose projects and existing Dockerfiles.

## Accepted implementation

- Frontend image: `apps/web/Dockerfile` (Next.js standalone runtime, non-root UID 1001).
- Backend image: `services/api/Dockerfile`, parameterized by `APP=api|worker|migrate`, distroless non-root runtime.
- Kustomize base manifests define the namespace, runtime ConfigMap, API Deployment/ClusterIP Service, web Deployment/ClusterIP Service, and worker Deployment.
- `deploy/k8s/migrations` defines a separate one-shot migration Job. Operators run and wait for the Job before applying or rolling out API and worker workloads.
- PostgreSQL/PgBouncer are external to the production Kustomize workload packages. The Docker Desktop helper dynamically provisions a local-only, single-replica PostgreSQL/PgBouncer Deployment and ClusterIP Service inside Kubernetes. This local database uses a bounded `emptyDir` and is disposable; it is not production or durable development storage.
- The local helper creates/reuses Kubernetes Secrets at runtime. It does not write credential values to disk or Git. API connects through PgBouncer; worker and migration connect directly to PostgreSQL.
- The API/web Deployments use two replicas, ClusterIP Services, readiness/liveness probes, and `maxUnavailable: 0` rolling-update settings. The worker uses one replica and a `Recreate` strategy.
- Pod security defaults include non-root identities, RuntimeDefault seccomp, no service-account token mount, no privilege escalation, read-only root filesystems, and dropped capabilities.
- The web workload has bounded writable `emptyDir` mounts for Next.js runtime cache and `/tmp`.
- Makefile targets build the web/API/worker/migration images and render both Kustomize packages. CI builds all four images without publishing them and validates both packages using pinned Kustomize v5.8.3.

## Runtime and rollout contract

1. For Docker Desktop local acceptance, run `scripts/k8s/provision-local-runtime.ps1`. The helper dynamically creates the local PostgreSQL/PgBouncer Deployment and ClusterIP Service inside the `flowlesshub` namespace. It generates or reuses database credentials in `flowlesshub-local-database-credentials`, waits for database readiness, then creates or verifies `flowlesshub-runtime-secrets`.
2. The local database is reached through Kubernetes service DNS: `flowlesshub-local-database:5432` for direct PostgreSQL connections and `flowlesshub-local-database:6432` for PgBouncer. The final runtime does not use the earlier separate Compose database or host-port bridge.
3. The runtime Secret contains `DATABASE_URL_API`, `DATABASE_URL_WORKER`, and `DATABASE_URL_MIGRATE`. API uses PgBouncer transaction pooling; worker and migration use direct PostgreSQL connections. Secret values must never be printed or committed.
4. Apply `deploy/k8s/migrations` and wait for `job/flowlesshub-migrate` to complete successfully. Inspect migration logs and retain the completed Job as evidence.
5. Only after migration completion, apply `deploy/k8s/base` and wait for API, web, and worker rollouts.
6. On a later release, delete the previous completed migration Job before creating a fresh Job; Kubernetes Jobs are immutable and a completed Job does not rerun on `apply`.
7. The local database uses `emptyDir` with a 2 GiB size limit. Its data is lost when its Pod is replaced or deleted. It is explicitly prohibited for production and durable development use.

The API readiness probe calls `/readyz` and reflects PgBouncer/database reachability. Liveness calls `/livez` and does not depend on PostgreSQL. The worker currently has no HTTP health endpoint; no fake liveness command is added. Its single-replica `Recreate` rollout gives the old process a SIGTERM shutdown window before replacement. River is responsible for its job shutdown/retry semantics.

## Image and environment policy

- CI builds four local validation tags: `flowlesshub-web:dev`, `flowlesshub-api:dev`, `flowlesshub-worker:dev`, and `flowlesshub-migrate:dev`. CI does not push images or create a registry/package.
- Manifest image names are local-development defaults. A real cluster rollout must use immutable image references from the selected registry. Mutable `dev` tags are prohibited in production.
- `flowlesshub-runtime-secrets` and `flowlesshub-local-database-credentials` are runtime-created Secrets and must not be committed. No passwords, real database URLs, Secret manifests, kubeconfigs, cluster credentials, or registry credentials enter Git.
- The frontend's `NEXT_PUBLIC_*` values are build-time inputs in Next.js. This slice does not invent a public API origin or change frontend build-time environment behavior.
- Production/remote clusters must provide managed PostgreSQL/PgBouncer endpoints and provision runtime secrets through the selected production secret manager.
- No production ingress, reverse proxy, TLS termination, blue/green traffic switch, HPA, NetworkPolicy, PostgreSQL StatefulSet, or PgBouncer Deployment is introduced by S0.7. The local helper's database resources are smoke-test-only and excluded from production Kustomize packages.

## Security and availability defaults

- Namespace enforces Kubernetes Pod Security `restricted` labels.
- API/web have two replicas and rolling update `maxUnavailable: 0`; they use ClusterIP only and receive Service traffic only when Ready.
- API/worker/migration use the existing distroless non-root image UID 65532.
- Web uses non-root UID 1001; only `.next/cache` and `/tmp` are writable through size-limited `emptyDir` mounts.
- No Kubernetes ServiceAccount token is mounted because these processes do not call the Kubernetes API.
- Migration Job runs once, sequentially, with a bounded active deadline and no parallelism.
- Local PostgreSQL is disposable and is not a production data store. Production credentials and database endpoints must come from production-managed infrastructure.
