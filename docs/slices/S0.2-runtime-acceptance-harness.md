# S0.2 — Disposable Runtime Acceptance Harness

**Status:** Harness committed on `32dc13661fa21d6822aa243d48e1d17775917065`; this follow-up fixes its stale exact-HEAD guard. S0.2 runtime acceptance remains pending until the script passes on the owner's Windows/Docker environment.

## Goal

Turn the existing S0.2 manual Compose acceptance procedure into a repeatable Windows PowerShell verification that exercises the real backend stack from a fresh, disposable PostgreSQL volume. The harness must produce evidence for the database/migration/worker path without changing application behavior or deleting the developer's existing Compose data.

## Scope

- Keep `scripts/validate-s0.2-runtime.ps1` anchored to audited baseline `c2cc54065cf49410538f4abed850567741dee813`, while allowing descendant commits that leave runtime-sensitive inputs unchanged.
- Check the baseline is an ancestor of HEAD and that Compose, runtime entry points, database configuration, migrations, and Go module inputs have not drifted since that baseline.
- Ignore unrelated documentation, harness, and line-ending-attribute changes when checking the runtime worktree; runtime-sensitive local modifications and untracked files still fail preflight.
- Generate a unique Compose project name for each run so the test volume and containers are isolated from the normal `flowlesshub-backend` project.
- Reject occupied host ports used by the backend Compose file before creating resources.
- Validate Compose configuration, build and start the stack, then assert migration exit success, PostgreSQL/PgBouncer health, API liveness/readiness, and worker stability.
- Assert API uses PgBouncer while River worker and migration service use direct PostgreSQL connections.
- Compare Docker container timestamps and assert API/worker start after the one-shot migration container finishes.
- Execute authenticated `SELECT 1` through PgBouncer.
- Prove readiness fails with HTTP 503 while PgBouncer is stopped, while liveness remains HTTP 200; restore PgBouncer and require readiness to recover.
- Re-run Goose and River migrations on the same disposable volume and assert successful completion without worker restarts.
- Capture service status and recent logs on failure. Remove only the unique disposable Compose project and its volume by default; `-KeepResources` is an explicit diagnostic escape hatch.

## Invariants

- No production/local Compose service definitions, application code, migration, dependency, generated artifact, or secret is changed.
- No existing named volume is reused or removed. The harness uses a per-run Compose project name and only calls `down --volumes` for that project.
- API request connections remain routed through PgBouncer transaction pooling.
- River's session-level `LISTEN`/`NOTIFY` connection remains direct to PostgreSQL.
- Migration service remains a one-shot direct PostgreSQL process that runs Goose then River migrations.
- No `CHECKPOINTS.md` box is changed by this harness.

## Positive acceptance tests

1. Compose configuration is valid and the backend images build.
2. Fresh PostgreSQL starts healthy.
3. Goose and River migrations complete and the one-shot `migrate` container exits `0`; API and worker container start timestamps are later than the migration finish timestamp.
4. PgBouncer becomes healthy and executes authenticated `SELECT 1` with result `1`.
5. API is running; `/livez` and `/readyz` both report success after dependencies recover.
6. API, worker and migration container environment confirms the required database routing.
7. River worker emits its bootstrap startup metadata and remains running without a restart during the stability window.
8. Goose and River migration rerun exits `0` on the same database volume, and API/worker remain healthy.

## Negative acceptance tests

- With PgBouncer stopped, `/livez` must remain HTTP `200` and `/readyz` must return HTTP `503`.
- Once PgBouncer is restored, its healthcheck must pass and `/readyz` must return `status=ok` again.
- A missing Docker daemon, an occupied host port, a HEAD that is not descended from the audited baseline, runtime-sensitive source/config drift, an unhealthy service, nonzero migration exit, or worker restart must fail the script rather than report a pass.

## Definition of Done for this harness

- PowerShell script and its reusable baseline guard are reviewed and committed with the slice spec and runbook.
- Owner runs it from a descendant of the audited baseline on Windows with Docker Desktop available; process exits `0` and reports all positive and negative assertions passed.
- The script removes only its own unique disposable Compose project/volume on success and failure unless `-KeepResources` is explicitly supplied.
- Frontend and backend CI pass on the owner-pushed commit.
- Existing S0.2 runtime slice documentation is updated with the resulting owner evidence in a later evidence-only closeout; no S0 checkbox is ticked by this harness patch.

## Explicit non-goals

- No production PgBouncer topology, TLS, HA/failover, pool sizing benchmark, database role split, RLS, tenant tables or production credentials.
- No Testcontainers dependency or CI container gate is added; this harness is an owner-run Windows/Docker runtime check.
- No production deployment, zero-downtime rollout or S0 exit-gate acceptance is claimed.
