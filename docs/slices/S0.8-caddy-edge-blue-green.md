# S0.8 — Caddy Edge, Blue/Green Traffic Switching, and Graceful Drain

**Status:** `CLOSED — OWNER ACCEPTED` for the S0.8 slice (owner confirmation recorded 13 November 2026). The broader S0 exit gate remains open.

## Goal

Add a controlled HTTP edge entrypoint and a reversible blue/green traffic-routing mechanism for the stateless web and API workloads. Make readiness, process liveness, and graceful shutdown explicit so an unready candidate cannot replace the currently serving edge.

## Decisions

- Use the official Caddy image pinned to `caddy:2.11.9-alpine`.
- Keep the existing `flowlesshub-api` and `flowlesshub-web` Services intact as compatibility aliases to the existing blue workloads.
- Add explicit `flowlesshub-api-blue`, `flowlesshub-api-green`, `flowlesshub-web-blue`, and `flowlesshub-web-green` ClusterIP Services. Their selectors are color-specific and never point at the worker or database.
- Keep both web/API colors deployed concurrently. The existing blue deployments retain two replicas; the initial green candidate has one replica for local resource economy. Production overlays/operators may scale green to the target capacity before activation.
- Caddy's config files are sourced from `deploy/k8s/base/caddy` through Kustomize `configMapGenerator`; there is one source of truth for local and production Caddy configuration. Kustomize retains the generated content hash and rewrites the edge Deployment's volume reference, so Caddyfile changes alter the Pod template and trigger a safe edge rollout.
- Caddy uses `FLOWLESSHUB_ACTIVE_COLOR` to select one color's API and web Services. Blue is the base default. `deploy/k8s/overlays/green` changes only that environment variable and triggers a safe Caddy rolling update.
- Edge Deployment has two replicas, `maxUnavailable: 0`, and `maxSurge: 1`. Its readiness exec probe checks both selected-color API `/readyz` and web `/` over Kubernetes Service DNS. A Caddy Pod cannot become Ready while either target is unavailable.
- The shared base keeps the edge Service as `ClusterIP`. The local overlay changes it to an HTTP-only NodePort on `30080` for Docker Desktop acceptance. The production overlay changes it to `LoadBalancer`, enables HTTPS, and mounts the externally supplied `flowlesshub-edge-tls` Secret. No TLS key or certificate is committed.
- Caddy uses its standard TLS defaults. The configuration does not override curves/cipher suites; Caddy's Go TLS stack can negotiate `X25519MLKEM768` where supported.
- API readiness is explicitly marked draining before shutdown. The process waits five seconds for endpoint/readiness propagation, then calls `http.Server.Shutdown` with a 25-second bound.
- Web Pods have a ten-second `preStop` endpoint-withdrawal propagation delay and a 45-second termination grace period. This hook is not a proof that every in-flight Next.js request drains before SIGTERM; a dedicated long-running request shutdown test or app-specific close handling remains required before production zero-downtime acceptance. Caddy uses a five-second shutdown delay and 25-second HTTP connection grace period, with a 35-second Pod termination grace period.
- River worker lifecycle and the existing worker `Recreate` strategy remain unchanged. The worker is not part of HTTP blue/green routing.

## Request routing contract

- `/api` and `/api/*` are sent to the selected API color. The `/api` prefix is stripped before proxying, so `/api/readyz` reaches the API's existing `/readyz` handler.
- All other paths are sent to the selected web color.
- `/_edge/livez` is served by Caddy itself and is used for edge process liveness.
- `/_edge/readyz` is a diagnostic route proxied to the selected API's `/readyz` and checks API/database readiness. Kubernetes edge Pod readiness separately checks both API and web.
- Caddy adds `X-FlowlessHub-Active-Color` to responses to make local switch/rollback evidence observable.
- The existing API and web ClusterIP Services remain unchanged for compatibility; new edge routing uses only the color-specific Services.
- The Admin API remains bound to loopback (`localhost:2019`) and is not exposed by a Kubernetes Service.

## Deployment and switch protocol

1. Complete database migrations before applying the workload base, following the S0.7 migration-first contract.
2. Apply `deploy/k8s/base`. Blue is active. Both green Deployments exist and the initial green Deployments run one replica each.
3. Build and tag the candidate images with immutable release identifiers for a real release. Update only the inactive color's API/web Deployments, and wait until both candidate Deployments are fully Available.
4. Verify the candidate color's API and web Services have ready endpoints. Probe the API through its color Service and the web through its color Service before switching.
5. Apply `deploy/k8s/overlays/green` to activate green. This changes the edge Pod template's active-color environment variable. Kubernetes keeps the previous ready edge Pods serving while replacement edge Pods start and pass readiness against the green API.
6. Wait for `deployment/flowlesshub-edge` to complete its rollout. Verify the edge response header reports `green`, the web root returns HTTP 200, and `/api/readyz` returns HTTP 200.
7. Retain the old color and its images until the rollback window closes. Rollback is `kubectl apply -k deploy/k8s/base` (blue default), followed by a successful edge rollout and smoke tests.
8. For subsequent releases, update the currently inactive color, stage it, then change the edge active color. Never overwrite the currently serving color before the candidate is healthy.

A failed switch is expected to leave old edge Pods available: if the target API is not Ready, replacement edge Pods fail readiness and `maxUnavailable: 0` prevents the old edge replicas from being removed. Operators must roll the active color back and investigate; do not force-delete old edge Pods.

## TLS and production boundary

- Local Docker Desktop uses HTTP on NodePort `30080`; no public hostname or TLS Secret is required.
- `deploy/k8s/overlays/production` switches the edge to a `LoadBalancer`, exposes ports 80/443, selects `Caddyfile.production`, and mounts `flowlesshub-edge-tls`.
- Before production apply, replace `FLOWLESSHUB_SITE_ADDRESS` in `flowlesshub-edge-runtime` with the real FQDN and provision a Kubernetes TLS Secret named `flowlesshub-edge-tls` from the production certificate/secret manager.
- The external certificate lifecycle is owned by the production certificate/secret manager. After TLS Secret rotation, trigger a controlled Caddy reload/rollout so the new mounted certificate is loaded.
- Caddy's standard TLS defaults are retained; do not hard-code obsolete cipher suites or remove the hybrid `x25519mlkem768` group. Confirm the edge handshake during production acceptance.
- The production overlay is rendered and validated by CI but is not applied by the local smoke runbook.

## Security and operational boundaries

- Edge Service is the only externally routed application entrypoint in this slice. The shared base keeps it ClusterIP-only; local NodePort and production LoadBalancer exposure are isolated to their respective overlays. API/web color Services and the legacy app Services remain ClusterIP.
- The Caddy Admin API is loopback-only. No Kubernetes ServiceAccount token is mounted.
- Caddy runs as non-root UID/GID 1000, with RuntimeDefault seccomp, read-only root filesystem, dropped capabilities, and only `NET_BIND_SERVICE` added to bind ports 80/443.
- Writable `/data`, `/config`, and `/tmp` are separate bounded `emptyDir` volumes. They are local/ephemeral; production TLS keys remain in a Kubernetes Secret supplied by a secret manager.
- No Secret data, private key, certificate, public hostname, registry credential, or database credential is committed.
- No WAF or third-party rate-limit plugin is added. Those controls require a separately selected and reviewed edge/security provider; do not imply that Caddy's basic reverse proxy is a WAF.
- No changes to database schema, Goose/River migrations, PostgreSQL/PgBouncer topology, API OpenAPI contract, or business behavior.
- No S0 checklist checkbox is changed. Local switch/rollback rehearsal is not the S0 production exit gate.

## Acceptance criteria

1. `make edge-validate` validates the local Caddyfile, adapts the production Caddyfile using the pinned Caddy image, and verifies that every blue/green Deployment selector matches its Pod-template label and Service selector.
2. `make k8s-build` renders base, migration, local, local-green, production, and production-green Kustomize packages.
3. Go readiness tests cover ready, dependency-unavailable, and draining states.
4. `go test ./...`, `go test -race ./...`, `go vet ./...`, Go formatting, architecture lint, module verification, and existing frontend quality gates pass.
5. CI validates the new Caddy configuration and all Kustomize packages.
6. Local Kubernetes has the blue and green API/web Services, two edge replicas, and the edge NodePort service.
7. A successful blue-to-green switch and green-to-blue rollback complete without edge unavailability; response header confirms the selected color.
8. A failed/unready candidate rehearsal proves the old edge replicas remain Ready because `maxUnavailable: 0`, after which the operator rolls back to the previous color.
9. Production overlay renders without embedded Secret data and clearly references the externally supplied TLS Secret.
10. The S0 production exit gate remains open until production hello-world, zero-downtime rollout, and rehearsed rollback are demonstrated.
