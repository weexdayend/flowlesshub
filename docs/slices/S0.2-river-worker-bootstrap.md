# S0.2 — River Worker Bootstrap Registration

**Status:** Patch prepared against `4efc335c8b74452769a464cdfffa41cb11fe9816`; owner validation and CI acceptance pending. S0.2 runtime acceptance remains open until the updated worker stays healthy in the disposable Compose stack.

## Context

The S0.2 Compose topology already runs Goose application migrations and River's versioned schema migrations before starting API and worker processes. The worker connects directly to PostgreSQL because River relies on session-level `LISTEN`/`NOTIFY` behavior that is not preserved by PgBouncer transaction pooling.

The initial worker entry point constructed `river.NewWorkers()` but registered no handlers. River v0.51.2 rejects `Client.Start()` when a configured worker client has an empty Workers bundle, producing `at least one Worker must be added to the Workers bundle`. The container therefore entered its restart loop even though Goose, River schema migrations, PgBouncer, and API startup succeeded.

## Decision

- Register one reserved platform bootstrap handler with River's `AddWorkerSafely` API.
- Use stable job kind `flowlesshub_platform_bootstrap_noop`.
- The handler has no domain behavior or side effects. It returns `ctx.Err()` so normal execution completes immediately and shutdown cancellation is respected.
- Do not enqueue this job as part of startup or use it as a substitute for business job handlers.
- Keep the default queue and direct PostgreSQL connection unchanged.
- Future business modules must register their own typed workers through the application worker composition root. The bootstrap handler remains only until the first real platform/business worker is introduced and can then be removed deliberately.

## Scope

- Add the bootstrap args/worker and a constructor that registers it using `river.AddWorkerSafely`.
- Replace the empty registry in `cmd/worker` with the constructed registry and fail startup with a contextual registration error if registration fails.
- Emit structured startup metadata for the reserved bootstrap kind while explicitly reporting that no business handlers are registered in S0.
- Add unit tests for registration, duplicate-kind rejection, normal no-op completion, and context cancellation.

## Invariants

- No database schema, migration, SQL query, queue name, worker concurrency, PgBouncer routing, or business module is changed.
- The worker keeps a direct PostgreSQL connection; API continues through PgBouncer.
- The reserved handler is not scheduled or enqueued automatically.
- No `CHECKPOINTS.md` acceptance box is modified by this patch.

## Definition of Done

1. `go test ./cmd/worker` passes and proves the handler is registered exactly once.
2. `go test ./...`, `go vet ./...`, module verification, Go formatting, and architecture lint pass.
3. Backend Docker Compose starts from a disposable empty volume; `migrate` exits `0`, API remains healthy, PgBouncer accepts `SELECT 1`, and the worker remains `running` without restart.
4. Worker logs contain the structured startup record and no empty-Workers-bundle error.
5. Re-running the migration service remains idempotent and does not destabilize the worker.
6. Owner pushes the patch and both frontend/backend CI jobs pass on the resulting HEAD.

## Non-goals

- No real business job handlers, schedules, periodic jobs, retries, or enqueue APIs are introduced.
- This patch does not close the full S0.2/S0 database checkpoint by itself; all other runtime and production exit-gate evidence remains independently required.
