# S0.2 — Database Runtime Pooling and Migration Orchestration

**Status:** Scaffolded as a local-development slice; owner runtime validation is pending. S0 remains open.

## Context

S0.1 established PostgreSQL connectivity, a Goose SQL migration directory, and a River worker process. The local Compose stack did not yet provide PgBouncer, did not run application/River migrations before starting dependants, and therefore could start the worker before the River schema existed.

## Decisions

- Pin the local PgBouncer image to `edoburu/pgbouncer:v1.26.1-p0`.
- Route API request traffic through PgBouncer in transaction pooling mode.
- Keep the River worker connected directly to PostgreSQL. River uses PostgreSQL `LISTEN`/`NOTIFY`; PgBouncer transaction pooling does not preserve the session affinity required by `LISTEN`.
- Run schema migrations as a one-shot `migrate` service before API and worker start.
- The migration command applies Goose-managed application SQL migrations first, then River's own versioned migrations using `rivermigrate`.
- Embed Goose SQL migration files in the migration binary so the distroless runtime image does not need the source tree mounted.
- Keep the PostgreSQL host port available for local administration and direct worker/migration connections; expose PgBouncer on host port `6432` for local diagnostics.

## Runtime flow

1. PostgreSQL becomes healthy.
2. The migration service connects directly to PostgreSQL, runs Goose migrations, then River migrations, and exits successfully.
3. PgBouncer becomes healthy and accepts API connections in transaction pooling mode.
4. API starts through PgBouncer after migration completion.
5. River worker starts directly against PostgreSQL after migration completion to retain `LISTEN`/`NOTIFY` semantics.

## Non-goals

- No tenant tables, RLS, application database role split, or production credential strategy; those remain S1/security work.
- No PgBouncer deployment for production, TLS termination, HA, failover, or pool sizing benchmark.
- No change to business modules or checkpoint completion marks.

## Validation required on the developer machine

- Run `go mod tidy` with Go 1.27.4 and commit updated `go.mod` plus `go.sum`.
- Run Go formatting, vet and tests, including the embedded migration test.
- Validate backend Compose configuration.
- Build the API, worker and migration images.
- Start the backend Compose project from an empty PostgreSQL volume; verify the migration service exits successfully before API/worker start.
- Verify API `/livez` and `/readyz`, and verify PgBouncer accepts an authenticated `SELECT 1` on host port `6432`.
- Verify River worker remains connected to direct PostgreSQL and starts without missing-table errors.
- Restart the stack using the same volume; both Goose and River migration steps must be idempotent.
