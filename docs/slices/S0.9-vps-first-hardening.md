## Goal

Establish and harden the existing VPS-first production delivery path using a dedicated Docker Compose project, pinned commit-addressed GHCR images, host Nginx plus a private Caddy edge, and Blue/Green traffic selection. Keep local workstation responsibilities limited to repository changes, Git, CI review, and patch validation; perform integration/runtime acceptance on the real VPS only when required.

## Architecture baseline

- Ubuntu 24.04 VPS, Docker Engine and Compose plugin.
- Dedicated Compose project `flowlesshub-vps` with isolated `flowlesshub-vps-edge` and `flowlesshub-vps-backend` networks.
- Named PostgreSQL data volume `flowlesshub-vps-postgres-data`; distinct Blue/Green Web cache volumes.
- Host Nginx remains the public `:80/:443` listener and TLS terminator. It routes Web domains to Caddy `127.0.0.1:3032` and API domain to Caddy `127.0.0.1:5052`.
- Caddy switches Web and API together between Blue and Green, using the matching Caddyfile and local admin API.
- PostgreSQL and PgBouncer ports are not published to the host/Internet. API uses PgBouncer transaction pooling; Worker and migrations connect directly to PostgreSQL.
- GHCR image tags are commit-addressed (`sha-<40-character-SHA>`). GitHub Actions builds/publishes the Web, API, Worker, and migration images; the VPS pulls images and does not build them.
- Production checkout is detached at an immutable release commit, not a moving `main` branch.

## Implementation decisions and hardening scope

### Deployment lifecycle and preflight

- `scripts/vps/preflight.sh` validates required tools, host/runtime preconditions, disk and memory headroom, Nginx state, loopback port ownership, deployment-lock support, `.vps-runtime/.env` mode `0600`, and Git ignore coverage.
- `scripts/vps/deploy-initial.sh` makes first installation resumable after partial FlowlessHub-only startup. It validates Compose, starts only the dedicated PostgreSQL/PgBouncer dependencies, waits for health, runs the one-shot migration, starts one color plus Worker and Caddy, probes private endpoints, and records the active color atomically.
- A failed first install must be inspected and resumed only after reviewing the exact FlowlessHub Compose state. The script refuses to overwrite unexpected runtime Caddy configuration. It does not require broad cleanup.

### Release and Blue/Green switching

- `scripts/vps/set-release.sh` updates only the inactive color and Worker/migration image references. It writes a protected temporary `.env`, validates Compose, then atomically installs the candidate values while holding the deployment lock.
- `scripts/vps/switch-color.sh` checks resource headroom before candidate start and before traffic switch, starts only the inactive API/Web pair, probes candidate readiness, validates its Caddyfile, reloads Caddy, verifies loopback routes, and updates active-color only after success.
- The previous active color remains available for rollback. A failed candidate operation leaves the active color selected and attempts to restore the prior Caddy config; an unconfirmed recovery retains a manual recovery copy.
- `scripts/vps/rollback-color.sh` restores traffic to the prior pinned color, validates its API/Web health, restores the Worker image reference to the same release, and keeps the deployment lock across the complete rollback sequence.
- `scripts/vps/update-worker.sh` verifies exactly one Worker container and observed River startup. Business handlers are not implied by this bootstrap state.

### CI and image publication gates

- CI validates tracked VPS scripts for executable mode `100755`, `bash -n`, and ShellCheck.
- CI validates the VPS Compose model with a non-secret fixture, both Caddy configurations, and the additive FlowlessHub Nginx site using temporary CI material.
- GHCR publication is gated on the tagged commit being reachable from `main` and successful push-triggered CI for the exact SHA.
- These checks prove source/configuration quality only. They do not prove the target VPS starts containers, has sufficient RAM for Blue/Green overlap, or serves public DNS/TLS routes.

## Safety and operational invariants

- Do not edit or replace existing Frictiona/Petshop Nginx virtual hosts. Install only the dedicated FlowlessHub virtual host.
- Do not stop, recreate, rename, or remove Petshop containers, databases, volumes, networks, or ports.
- Do not attach FlowlessHub to Petshop networks or volumes.
- Do not publish FlowlessHub PostgreSQL/PgBouncer ports.
- Do not use global Docker prune or `docker compose down -v`.
- Preserve the 2 GiB VPS memory guards. If the host cannot safely start the inactive color, stop; do not lower thresholds.
- Application rollback does not roll back a database migration. Use expand/contract compatibility. Database restore is disaster recovery, not release rollback.
