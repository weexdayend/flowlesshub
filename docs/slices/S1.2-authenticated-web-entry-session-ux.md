# S1.2 — Authenticated Web Entry and Session UX

**Status:** Strategy/specification prepared for owner review; implementation not started.
**Depends on:** S1.1 accepted backend/API release `495383f38ec7c356b97bb66017b66a3380130eaf`.
**Current documentation baseline:** `c6e31e03204de8035af9ef0bf2e0f0f187f8f297`.
**Roadmap:** [`PRODUCTION-GRADE-PSA-ROADMAP.md`](../roadmap/PRODUCTION-GRADE-PSA-ROADMAP.md).

## 1. Business outcome

An existing S1.1 user can access FlowlessHub through a real browser authentication experience:

1. A user can sign in with the existing account.
2. The browser can restore an unexpired server-backed session without exposing the opaque session token to JavaScript.
3. Anonymous users cannot access authenticated application routes or authenticated data.
4. A user can sign out; the server revokes the session and the browser loses access.
5. An expired, revoked or disabled-user session returns the user to a recoverable sign-in state.
6. The authenticated shell identifies the user and the active organization memberships returned by the S1.1 API. No tenant business data is exposed in this slice.

This is the first S1.2 implementation workstream. It does not reopen S1.1, alter its accepted backend/API scope, or claim that customer or other PSA business workflows exist.

## 2. Repository facts and boundary

At baseline `c6e31e03204de8035af9ef0bf2e0f0f187f8f297`:

- The Go API exposes `POST /v1/auth/login`, `POST /v1/auth/logout`, `GET /v1/auth/me` and `GET /v1/organizations`.
- The S1.1 session token is opaque and stored in PostgreSQL as a SHA-256 digest. Production cookie configuration uses the `__Host-flowlesshub_session` name, `HttpOnly`, `Secure`, host-only scope and `SameSite=Lax`.
- The API's configured production web origin defaults to `https://app.flowlesshub.com`; the API host is `api.flowlesshub.com`.
- The API cookie is host-only to the API host. The `app.flowlesshub.com` server cannot receive or read that cookie in its own Next.js request, middleware or server component.
- `apps/web/src/app/page.tsx` is currently a preview shell. No `/sign-in` route, authenticated route group, server-side session bridge or organization context exists.
- The API login limiter is process-local. It is not a shared/global counter across concurrently active API instances.

No browser auth implementation or new database structure is assumed by this specification.

## 3. Mandatory architecture decision before implementation

Create an ADR for **Browser Session Topology: Direct API Cookie vs Next.js BFF**.

The ADR must evaluate:

- Server-side authentication and protected route behavior in Next.js.
- Cookie host, prefix, path, Secure/HttpOnly/SameSite flags and expiration.
- Whether browser requests call the API origin directly or call a same-origin Next.js BFF.
- How an opaque API session is forwarded server-to-server without exposing it to browser JavaScript.
- Cookie creation/clearing, session introspection, logout/revocation and expiry behavior.
- Exact Origin and CSRF protections for every state-changing path.
- CORS/credential behavior, request size/timeouts and safe error propagation.
- API and web Blue/Green overlap, deployment compatibility and rollback.
- Testability of malicious origin, forged organization context, stolen/replayed cookie and concurrent sign-out.

**Proposed default, not an owner-approved decision:** a same-origin Next.js BFF is the preferred path because it can enforce protected routes on the server while the current API session cookie is scoped to `api.flowlesshub.com`. The ADR must confirm whether the BFF should re-issue an HttpOnly host-only app cookie and proxy the session to the API, or use another scheme. Never solve the SSR gap by putting a raw session token in JavaScript or browser storage.

Do not proceed to feature code until this ADR and its security tests are reviewed.

## 4. Functional scope

### 4.1 Public authentication routes

- Sign-in form with normalized email input behavior consistent with the API and a password field that never persists or echoes the secret.
- Generic invalid-credential feedback that does not reveal whether an account exists or is disabled.
- Loading, rate-limited, network-failure and service-unavailable states.
- Accessible field labels, keyboard behavior, focus management and responsive layout.

### 4.2 Session lifecycle

- On page/request load, validate the existing session through the approved server-side path.
- No session or invalid session: route to sign-in without rendering protected content.
- Valid session: render the authenticated application shell and user identity.
- Sign-out: revoke the server session, clear the browser cookie and redirect to sign-in.
- Expiry/revocation during use: handle `401` consistently; no infinite redirect loop.
- Session state must be revalidated server-side; client cache is not proof of authentication.
- Preserve S1.1's fixed session lifetime and revocation semantics unless a separately approved ADR changes them.

### 4.3 Protected application shell

- Root/overview route is no longer an anonymous static dashboard.
- Authenticated shell shows the current user's identity and active organization memberships returned by the API.
- Organization choice is contextual state only; it does not grant access. The backend revalidates membership and permissions for every tenant request.
- Navigation labels are not implemented capabilities. Unbuilt modules must not be represented as usable routes or populated with fake operational data.
- Explicit empty/foundation state is allowed, with honest capability availability.

## 5. Security and correctness requirements

- Never expose a raw session token in HTML, JSON, URLs, client components, `localStorage`, `sessionStorage`, logs or telemetry.
- Cookie and CSRF/Origin behavior is derived from the accepted ADR and tested in a real browser.
- All authentication and logout operations preserve exact Origin policy and generic errors.
- Add tests for valid sign-in, bad credentials, disabled user, session expiry, revocation, replay, logout idempotency, concurrent tabs, service outage and invalid cookie.
- Test direct navigation to every protected route, not only navigation through the UI.
- Test that API calls fail when session is absent, expired, revoked, or when the selected organization is not a current active membership.
- Address the process-local API login limiter: select an enforceable cross-instance strategy or document a proven edge limit with owner approval. Do not call the current in-memory limiter a global rate limit.
- Apply security headers/CSP and prevent credential/session values from entering logs or error output.
- Do not add business tables or bypass the upcoming S1.3 RLS/runtime-role gate.

## 6. API and data contract

Prefer reusing S1.1 operations and schemas. Any required API change must begin in `api/openapi.yaml`, regenerate Go/TypeScript output through repository commands, and include contract tests.

Expected API behavior remains:

| Operation | Required behavior |
|---|---|
| `POST /v1/auth/login` | Verify existing credentials; establish only a secure server-backed session. |
| `POST /v1/auth/logout` | Idempotently revoke the current session and clear the cookie. |
| `GET /v1/auth/me` | Return safe user/session data and active memberships. |
| `GET /v1/organizations` | Return only active memberships for the authenticated user. |

Do not add signup, invitation, password reset, email verification, SSO, MFA or organization mutation endpoints in S1.2 unless the owner explicitly expands the scope through an ADR and roadmap update. Membership lifecycle is assigned to S1.3.

No new migration is expected by default. If a migration is proposed, explain why the existing S1.1 session model cannot satisfy the requirement, demonstrate backward compatibility with the accepted release and keep production migration/deployment outside this docs specification.

## 7. Observability and operability

- Record auth outcome categories and correlation IDs without logging email/password/token/cookie values.
- Expose actionable counts/latency for login success/failure, rate-limit rejection, session validation failure and logout failure.
- A failed API or session store must produce a bounded, understandable unavailable state; it must not authenticate optimistically.
- Document cookie/session diagnostics, clock/timezone assumptions, API dependency behavior, support steps and rollback implications.
- Validate that a Blue/Green overlap does not produce inconsistent cookie names, origin policy or session behavior.

## 8. Acceptance criteria

S1.2 can be accepted only when all applicable cases pass:

- [ ] Approved ADR establishes browser session topology and threat controls.
- [ ] User can sign in with a provisioned S1.1 account.
- [ ] Successful response establishes only an HttpOnly, Secure, host-only, correctly scoped cookie; no token appears in browser-readable state.
- [ ] Session restoration works on refresh and direct protected-route navigation.
- [ ] Anonymous, expired, revoked and disabled-user sessions cannot render protected content or call protected data successfully.
- [ ] Logout revokes the server session and clears the browser cookie; replay is rejected.
- [ ] Invalid Origin/CSRF attempts are rejected; credentialed CORS is not used as a CSRF substitute.
- [ ] Login abuse controls are verified across the deployed API topology.
- [ ] Identity and organization context are safe; changing organization IDs never bypasses membership checks.
- [ ] Browser tests cover success, invalid credentials, outage, rate limit, expiry, logout, multi-tab and route access.
- [ ] Generated API output is stable; frontend lint/typecheck/build and backend tests/race/vet pass on the exact SHA.
- [ ] Exact-SHA GitHub Actions jobs pass; no VPS action is claimed unless separately authorized and evidenced.
- [ ] Runbook, acceptance evidence and `CHECKPOINTS.md` record actual outcomes; owner explicitly accepts the slice.
