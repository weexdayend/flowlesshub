# S1.2 — Passwordless Identity, First-Party SSO and Authenticated Web Entry

**Status:** Owner-approved scope amendment; ADR-0001 accepted; implementation not started.
**Depends on:** S1.1 accepted backend/API release `495383f38ec7c356b97bb66017b66a3380130eaf`.
**Current documentation baseline:** `92aec75c6387d6f57a1dc0d71c5ab7431f5831cd`.
**Roadmap:** [`PRODUCTION-GRADE-PSA-ROADMAP.md`](../roadmap/PRODUCTION-GRADE-PSA-ROADMAP.md).

## 1. Business outcome

An existing S1.1 user can access FlowlessHub through a real browser authentication experience:

1. A user can sign in with the existing account.
2. The browser can restore an unexpired server-backed session without exposing the opaque session token to JavaScript.
3. Anonymous users cannot access authenticated application routes or authenticated data.
4. A user can sign out; the server revokes the session and the browser loses access.
5. An expired, revoked or disabled-user session returns the user to a recoverable sign-in state.
6. The authenticated shell identifies the user and the active organization memberships returned by the S1.1 API. No tenant business data is exposed in this slice.

This is the first S1.2 implementation workstream. It does not reopen S1.1, alter its accepted backend/API scope, or claim that customer or other PSA business workflows exist.

## 2. Repository facts and boundary

The following application facts were verified at code baseline `c6e31e03204de8035af9ef0bf2e0f0f187f8f297`, the parent of the documentation-only baseline `92aec75c6387d6f57a1dc0d71c5ab7431f5831cd`:

- The Go API exposes `POST /v1/auth/login`, `POST /v1/auth/logout`, `GET /v1/auth/me` and `GET /v1/organizations`.
- The S1.1 session token is opaque and stored in PostgreSQL as a SHA-256 digest. Production cookie configuration uses the `__Host-flowlesshub_session` name, `HttpOnly`, `Secure`, host-only scope and `SameSite=Lax`.
- The API's configured production web origin defaults to `https://app.flowlesshub.com`; the API host is `api.flowlesshub.com`.
- The API cookie is host-only to the API host. The `app.flowlesshub.com` server cannot receive or read that cookie in its own Next.js request, middleware or server component.
- `apps/web/src/app/page.tsx` is currently a preview shell. No `/sign-in` route, authenticated route group, server-side session bridge or organization context exists.
- The API login limiter is process-local. It is not a shared/global counter across concurrently active API instances.

No browser-auth implementation or S1.2-specific identity schema is assumed to exist at the code baseline. S1.2 explicitly plans additive structures only where required for WebAuthn credentials/challenges, recovery-code verifiers, OIDC client/authorization state, and a minimal Identity-to-BFF session binding proven necessary by S1.2-A.

## 3. Accepted architecture and S1.2-A implementation gate

**Accepted architecture:** [ADR-0001 — Passwordless Identity and First-Party OIDC SSO](../architecture/ADR-0001-passwordless-identity-and-first-party-oidc.md) is the owner-accepted target architecture for S1.2. It supersedes the earlier proposal to compare direct API-cookie access with a Next.js BFF. The selected target is:

- The internally managed Go Identity authority remains the source of truth for global identities, credentials, central sessions and first-party OIDC.
- WebAuthn/FIDO2 passkeys are the primary passwordless authenticator; registration and authentication require `userVerification=required`. Credential backup eligibility/state is recorded separately from user-verification and MFA evidence.
- First-party SSO uses OpenID Connect Authorization Code Flow with PKCE `S256`, registered clients and exact redirect URIs.
- Next.js uses a same-origin BFF with a distinct host-only application session. Identity/API and application cookies remain host-only; browser cookies are never assumed to cross between `app.flowlesshub.com` and `api.flowlesshub.com`.
- Owner-provided SMTP is integrated through a server-side adapter and durable transactional outbox. Email is for address confirmation and notifications, never login, MFA, step-up or account-recovery proof.
- S1.1 users, Argon2id hashes and accepted central sessions remain compatible through an additive, staged transition.

**S1.2-A remains a mandatory implementation-readiness gate, not a second architecture-selection exercise.** Before feature code or migrations, S1.2-A must produce and review:

- Frozen, explicit production and development configuration for the browser origin, WebAuthn RP ID, OIDC issuer identifier, discovery/JWKS and authorization/token endpoints. No security origin may be inferred from request `Host`, `Origin` or untrusted forwarded headers.
- A client registry contract covering each first-party `client_id`, exact callback URI, audience, scopes, confidential-client authentication, logout behavior and signing-key rotation.
- A browser-tested Authorization Code + PKCE handoff that reconciles the app-origin BFF session with the API-host Identity session server-to-server. It must not rely on the browser sending a host-only cookie to another host, expose central cookies/tokens, or broaden cookie scope. The exact same-origin authorization route and callback sequence must be proven before registration is enabled.
- The BFF session-binding/revocation model, cookie attributes, CSRF/Origin rules, CORS policy, session expiry/rotation, API revalidation, Blue/Green compatibility and rollback behavior.
- WebAuthn ceremony, origin/RP ID, challenge lifecycle, authenticator evidence, credential backup metadata, assurance classification and negative-test contract.
- Recovery threat model, one-time recovery-code lifecycle, support verification and separation-of-duties controls; email possession is never accepted as recovery proof.
- Cross-instance login/WebAuthn abuse-control design and exact rate-limit ownership; the existing process-local S1.1 login limiter is not described as a global control.
- Owner-supplied SMTP settings verified out of band, including TLS certificate validation, sender identity and SPF/DKIM/DMARC readiness. Credentials remain outside source control and chat.
- Browser/integration test cases for sign-in, passkey ceremonies, OIDC state/nonce and callback validation, BFF/API session boundary, logout, revocation, replay, origin forgery, outages and mixed-version operation.

Do not begin S1.2 feature implementation until the S1.2-A artifacts, threat analysis and browser interoperability evidence have been reviewed. ADR-0001 accepts the target architecture; it does not assert that the BFF handoff, production origins, passkey registrations, OIDC clients, SMTP delivery or runtime behavior are implemented or already accepted.

## 4. Functional scope

### 4.1 Public authentication routes

- Passkey-first sign-in using the approved WebAuthn ceremony and normalized account identifier where account discovery is needed; do not reveal whether an account exists.
- Keep the S1.1 password path only as a controlled, rate-limited migration fallback until the measured password-retirement gate is separately approved. Do not present email OTP or magic-link as a fallback authenticator.
- Authenticated users can enroll and manage multiple passkeys/security keys after recent reauthentication; first-passkey enrollment requires a currently authenticated S1.1 session or an equivalent independently verified owner process.
- Generic invalid-credential feedback that does not reveal whether an account exists or is disabled.
- Loading, rate-limited, network-failure and service-unavailable states.
- Accessible field labels, keyboard behavior, focus management and responsive layout.

### 4.2 Session lifecycle

- On page/request load, validate the existing session through the approved server-side path.
- No session or invalid session: route to sign-in without rendering protected content.
- Valid session: render the authenticated application shell and user identity.
- Sign-out: revoke the server session, clear the browser cookie and redirect to sign-in.
- Expiry/revocation during use: handle `401` consistently; no infinite redirect loop.
- Session state must be revalidated server-side; client cache is not proof of authentication.
- Preserve S1.1's fixed session lifetime and revocation semantics unless a separately approved ADR changes them.

### 4.3 Protected application shell

- Root/overview route is no longer an anonymous static dashboard.
- Authenticated shell shows the current user's identity and active organization memberships returned by the API.
- Organization choice is contextual state only; it does not grant access. The backend revalidates membership and permissions for every tenant request.
- Navigation labels are not implemented capabilities. Unbuilt modules must not be represented as usable routes or populated with fake operational data.
- Explicit empty/foundation state is allowed, with honest capability availability.

## 5. Security and correctness requirements

- Never expose a raw session token in HTML, JSON, URLs, client components, `localStorage`, `sessionStorage`, logs or telemetry.
- Cookie and CSRF/Origin behavior is derived from the accepted ADR and tested in a real browser.
- All authentication and logout operations preserve exact Origin policy and generic errors.
- Add tests for valid sign-in, bad credentials, disabled user, session expiry, revocation, replay, logout idempotency, concurrent tabs, service outage and invalid cookie.
- Test direct navigation to every protected route, not only navigation through the UI.
- Test that API calls fail when session is absent, expired, revoked, or when the selected organization is not a current active membership.
- Address the process-local API login limiter: select an enforceable cross-instance strategy or document a proven edge limit with owner approval. Do not call the current in-memory limiter a global rate limit.
- Apply security headers/CSP and prevent credential/session values from entering logs or error output.
- Do not add business tables or bypass the upcoming S1.3 RLS/runtime-role gate.
- WebAuthn challenges are cryptographically random, short-lived, purpose-bound, user/session-bound and atomically single-use; validate exact origin, reviewed RP ID, RP ID hash, credential ownership, signature and user-verification evidence.
- OIDC authorization codes are short-lived, single-use and PKCE-bound; validate exact redirect URI, state, nonce, issuer, audience, signature and token lifetime. Discovery/JWKS/key rotation and mix-up protection are part of the server contract.
- Prove the app-origin BFF / API-origin Identity handoff in a real browser. A host-only cookie must never be assumed to cross its host boundary. Test login, authorization redirect, callback, logout, revocation and multi-client SSO.
- SMTP delivery is asynchronous and idempotent. SMTP outage, bounce, retry exhaustion and manual repair must be observable; sender configuration and secrets are redacted.

## 6. API and data contract

Prefer reusing S1.1 operations and schemas. Any required API change must begin in `api/openapi.yaml`, regenerate Go/TypeScript output through repository commands, and include contract tests.

Expected API behavior remains:

| Operation | Required behavior |
|---|---|
| `POST /v1/auth/login` | Verify existing credentials; establish only a secure server-backed session. |
| `POST /v1/auth/logout` | Idempotently revoke the current session and clear the cookie. |
| `GET /v1/auth/me` | Return safe user/session data and active memberships. |
| `GET /v1/organizations` | Return only active memberships for the authenticated user. |

The owner-approved scope amendment in Section 10 explicitly includes WebAuthn passkey registration/authentication/revocation, first-party OIDC SSO, BFF session binding/revocation, SMTP transactional notifications/address confirmation, and controlled account recovery as specified by ADR-0001. Public self-service signup, customer/vendor portal workflows, customer-owned enterprise IdP federation, SAML, SCIM and organization membership mutation remain outside S1.2. Organization membership lifecycle and role policy remain assigned to S1.3.

Additive migrations are expected only for WebAuthn credentials/challenges, recovery-code verifiers, OIDC client/authorization state, and the minimal server-side Identity-to-BFF session binding proven necessary by S1.2-A. Exact tables/columns and constraints are not invented by this slice; the implementation ADR must define them. Use expand/migrate/switch/contract, prove compatibility with the accepted S1.1 release, preserve existing sessions, and provide rollback. No destructive identity migration or production migration/deployment is authorized by this documentation specification.

## 7. Observability and operability

- Record auth outcome categories and correlation IDs without logging email/password/token/cookie values.
- Expose actionable counts/latency for login success/failure, rate-limit rejection, session validation failure and logout failure.
- A failed API or session store must produce a bounded, understandable unavailable state; it must not authenticate optimistically.
- Document cookie/session diagnostics, clock/timezone assumptions, API dependency behavior, support steps and rollback implications.
- Validate that a Blue/Green overlap does not produce inconsistent cookie names, origin policy or session behavior.

## 8. Acceptance criteria

S1.2 can be accepted only when all applicable cases pass:

- [ ] Accepted ADR-0001 is realized through a reviewed S1.2-A implementation contract, threat analysis and browser-proven BFF/OIDC handoff.
- [ ] User can sign in with a provisioned S1.1 account.
- [ ] Successful response establishes only an HttpOnly, Secure, host-only, correctly scoped cookie; no token appears in browser-readable state.
- [ ] Session restoration works on refresh and direct protected-route navigation.
- [ ] Anonymous, expired, revoked and disabled-user sessions cannot render protected content or call protected data successfully.
- [ ] Logout revokes the server session and clears the browser cookie; replay is rejected.
- [ ] Invalid Origin/CSRF attempts are rejected; credentialed CORS is not used as a CSRF substitute.
- [ ] Login abuse controls are verified across the deployed API topology.
- [ ] Identity and organization context are safe; changing organization IDs never bypasses membership checks.
- [ ] Browser tests cover success, invalid credentials, outage, rate limit, expiry, logout, multi-tab and route access.
- [ ] Generated API output is stable; frontend lint/typecheck/build and backend tests/race/vet pass on the exact SHA.
- [ ] Exact-SHA GitHub Actions jobs pass; no VPS action is claimed unless separately authorized and evidenced.
- [ ] Runbook, acceptance evidence and `CHECKPOINTS.md` record actual outcomes; owner explicitly accepts the slice.
- [ ] User can enroll multiple passkeys/security keys from an authenticated existing account and sign in with `userVerification=required`; challenge replay, wrong origin/RP ID, wrong user, wrong signature and revoked credential are rejected. Credential `BE`/`BS` backup flags are persisted; `BE` immutability and valid `BE`/`BS` combinations are enforced.
- [ ] Authentication assurance records actual WebAuthn user-verification/authenticator evidence; events that do not meet a policy MFA requirement cannot satisfy it. No AAL or certification claim is made without assessment.
- [ ] First-party OIDC SSO passes Authorization Code + PKCE `S256`, exact redirect URI, state/nonce, issuer, signature, `aud`/`client_id`, matching `azp` when present, and time validation, single-use code and token replay tests. Untrusted additional audiences are rejected. Implicit and password grants are absent.
- [ ] App-host and API-host session boundaries are proven; OIDC front-channel handoff works without sharing cookies across hosts or widening cookie domain. Tokens and Identity-session secrets remain server-side.
- [ ] SMTP TLS, sender identity and SPF/DKIM/DMARC are verified from owner-supplied settings; outbox delivery, deduplication, retries, bounce/failure state and secret redaction pass. Email OTP/magic-link cannot authenticate or recover an account.
- [ ] Existing S1.1 users can enroll without mass logout or destructive migration; existing session revocation and rollback remain compatible.
- [ ] Recovery codes are single-use, stored as verifiers, rate-limited and audited; loss-of-authenticator recovery requires independent verification and separation of duties.

## 10. Owner-approved identity scope amendment — 14 November 2026

This section is an explicit owner-approved expansion of S1.2. It supersedes the earlier S1.2 exclusions that named SSO, MFA, account recovery and email verification as out of scope. S1.1 remains closed exactly as accepted; no production identity behavior is changed by this documentation amendment.

### 10.1 Decisions

1. FlowlessHub retains an internally managed Identity authority in the existing Go modular monolith. First-party SSO is OpenID Connect; no external identity SaaS is introduced as a runtime dependency.
2. WebAuthn/FIDO2 passkeys are the primary passwordless authentication method. Registration and assertion require `userVerification=required`. Server verification binds each ceremony to a short-lived, single-use challenge, exact origin and reviewed RP ID; validates ceremony type, RP ID hash, user verification/presence, public-key signature and credential ownership. Multiple passkeys and roaming security keys are supported.
3. MFA assurance is evidence-based. Record whether the authenticator performed local activation/user verification and classify single-factor versus multi-factor cryptographic events. Do not treat email access, a typed OTP, or an unverified passkey property as phishing-resistant MFA. Do not claim a NIST AAL or regulatory certification without assessment. S1.3 maps assurance requirements to privileged roles/permissions.
4. First-party OIDC clients use Authorization Code Flow + PKCE `S256`, exact redirect URI registration, transaction-specific `state`/`nonce`, issuer identification, signature/issuer/audience/time validation, short-lived single-use codes and bounded scopes/audiences. Implicit and Resource Owner Password Credentials grants are prohibited.
5. Next.js uses a same-origin BFF. The existing API-host Identity session and the app-host BFF session are separate host-only cookies and separate server-side session records. Tokens remain server-side. Do not widen the cookie to `.flowlesshub.com` to make SSR work.
6. Existing SMTP domain is used for transactional email: email-address confirmation, security notices, recovery notifications and later user invitations. Delivery is asynchronous through a durable outbox with idempotent retry. SMTP credentials are protected runtime secrets. Email OTP, magic-link login and mailbox access are not authentication/MFA/step-up factors.
7. Keep S1.1 password hashes and session compatibility during staged migration. Existing users enroll passkeys from an authenticated session. Do not remove password compatibility or invalidate all sessions until enrollment, recovery, support and rollout acceptance are proven and a separate retirement policy is approved.
8. A global identity is separate from organization membership and customer/vendor relationships. Future customer/vendor users receive explicit delegated/project-scoped access, not automatic membership in the service-provider tenant.

### 10.2 Configuration decisions and pre-implementation gates

- Existing production web/API origins are `https://app.flowlesshub.com` and `https://api.flowlesshub.com`. The initial OIDC issuer target is the API origin. The approved WebAuthn ceremony surface is the first-party login surface on the app origin; its exact RP ID and allowed origin must be frozen as exact values in S1.2-A before any credential is registered. No wildcard parent-domain trust is allowed. Development origins are separate explicit configuration.
- The exact SMTP hostname, port, TLS mode, sender address, authentication method and secret path must be verified from the owner's existing mail service. Do not invent or commit credentials. Production send is blocked until SMTP TLS, sender authentication, SPF, DKIM and DMARC alignment are verified.
- The exact BFF session store/binding schema, OIDC client identifiers, callback URIs, scopes, audiences, signing-key rotation, cookie names and session lifetime are fixed in the S1.2-A implementation ADR before code/migration. Preserve `__Host-` requirements and S1.1 revocation semantics.
- Use maintained, security-reviewed Go WebAuthn and OIDC/OAuth libraries. Do not implement cryptographic protocol verification or JWT/OIDC validation primitives from scratch. Pin reviewed versions and record the dependency/upgrade policy.

### 10.3 Phase exit gates

- **S1.2-A — Architecture and threat model:** approve issuer/login/RP origins, OIDC clients, BFF cookies/session binding, CSRF/Origin behavior, authenticator assurance, recovery, account migration and threat model.
- **S1.2-B — SMTP delivery:** validate owner-supplied SMTP configuration and DNS authentication; build outbox, worker delivery, retry/deduplication, bounce/failure visibility and secret redaction.
- **S1.2-C — Passkeys:** additive credential/challenge storage, registration, authentication, revocation, multiple credentials, rate limits and WebAuthn negative/interoperability tests.
- **S1.2-D — OIDC/BFF SSO:** internal issuer, client registry, Authorization Code + PKCE, server-side token exchange/storage, protected routes, app session creation/rotation/revocation and first-party SSO tests.
- **S1.2-E — Recovery and security policy:** one-time recovery codes, additional authenticator enrollment, notifications, manual recovery process, assurance classification and step-up hooks.
- **S1.2-F — Migration and production acceptance:** coexistence with S1.1, session/revocation/Blue-Green tests, browser tests, rate limiting across API instances, secret/DNS/SMTP review, exact-SHA CI and owner acceptance.

S1.2 does not implement enterprise federation to customer-owned identity providers, SAML, SCIM, self-service signup, customer/vendor portal workflows, tenant-owned business data or the S1.3 role/tenant authorization and RLS work. These remain later slices with their own authorization and acceptance gates.
