# S0.5 — Hybrid PQ TLS Handshake Verification

**Status:** Patch prepared against `7b6394330b741500311429bf141831181d728017`; owner validation and CI acceptance pending. S0 remains open.

## Context

The Technical Architecture requires TLS 1.3 with the hybrid `X25519MLKEM768` key exchange and explicitly calls for an automated handshake test in CI. The current repository uses Go 1.27.4, whose `crypto/tls` package exposes `tls.X25519MLKEM768`.

The existing runtime acceptance proved the local API, PostgreSQL and PgBouncer startup path. It did not exercise or assert the negotiated TLS key-exchange group.

## Decision

- Add a standard-library integration test under `internal/platform/transportsecurity`.
- Run an in-process HTTPS server and client using `httptest`.
- Constrain both endpoints to TLS 1.3 and the single `tls.X25519MLKEM768` key-exchange group.
- Assert the handshake succeeds, the negotiated protocol is TLS 1.3, and the negotiated group is exactly `X25519MLKEM768`.
- Rely on the existing backend CI `go test ./...` job to execute the test; no third-party dependency or workflow change is needed.

The test intentionally constrains both peers to one group. A successful request therefore cannot silently fall back to classical X25519 or another key exchange.

## Scope

- Add the `transportsecurity` package documentation.
- Add one deterministic local TLS handshake integration test.
- Keep the test isolated from application configuration and runtime endpoints.

## Security interpretation and limits

This test proves that the repository's Go TLS client/server stack can negotiate the named hybrid key exchange when both peers explicitly permit it.

It does **not** prove:
- That production traffic currently terminates with TLS 1.3 or this key exchange.
- That a future Caddy/Traefik/CDN edge, WAF, load balancer, browser, or customer network supports the group.
- That the TLS server certificate or certificate authority uses post-quantum signatures. Server authentication remains classical under the architecture's current stated ecosystem limits.
- That the overall deployment has been externally penetration-tested or production-certified.

A later reverse-proxy/deployment slice must verify the negotiated group against the actual selected edge terminator and its supported client population.

## Invariants

- No runtime TLS listener, certificate, proxy, Compose service, Kubernetes manifest, or production traffic path is changed.
- No TLS downgrade or fallback policy is introduced.
- No Go module dependency or generated artifact is changed.
- No `CHECKPOINTS.md` item or S0 exit gate is marked complete by this sub-slice.
