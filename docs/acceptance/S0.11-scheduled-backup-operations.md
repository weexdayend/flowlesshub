## Review correction validation (12 November 2026)

The review identified that systemd's `ProtectHome=true` hides the `ubuntu` home directory while Restic normally places its cache under `$XDG_CACHE_HOME/restic` or `~/.cache/restic`. The service now sets `RESTIC_CACHE_DIR=/tmp/flowlesshub-restic-cache`; `PrivateTmp=true` keeps that cache private to the unit.

The remote upload flow now reads the archive, checksum sidecar, and manifest back from the exact tagged Restic snapshot using `restic dump`, then compares all three remote SHA-256 values with their local files before creating the marker. Retention accepts only the versioned marker format and validates archive/sidecar/manifest hashes. The final `--apply` deletion loop repeats the exact tagged snapshot lookup and reads all three remote files again for each candidate, then rechecks the local files and marker before removing that artifact group.

## Final review hardening (12 November 2026)

The final local review found two additional correctness/safety gaps and one documentation consistency gap:

- A string-prefix test on `RESTIC_PASSWORD_FILE` could accept a path such as `.vps-runtime/../outside/password`. Both off-site upload and retention now resolve the configured password path with `realpath -e` and require the canonical path to remain beneath the canonical `.vps-runtime` directory. Existing regular-file, non-symlink, owner, and `0600` checks remain.
- Retention's initial candidate scan now performs only eligibility checks. During `--apply`, a dedicated final deletion loop revalidates the complete local artifact triplet and marker, re-lists the exact tagged Restic snapshot, reads the archive/checksum/manifest back from that exact snapshot, compares their SHA-256 values, rechecks the local files/marker, and only then removes that single artifact group. No later candidate is processed between that final read-back and the current group's removal.
- The README/AGENTS/CHECKPOINTS/runbook fresh-session read order is now consistent: canonical operating runbook first, then README, AGENTS, CHECKPOINTS, then the active checkpoint documents.

## Acceptance boundary

- A systemd timer parsing successfully is not proof that a scheduled backup ran.
- A Restic snapshot listing is not proof that archive data can be read. The uploader now reads back the archive triplet and compares hashes before writing a marker; this targeted check is still not a PostgreSQL restore drill or full remote-repository integrity audit.
- A local marker is not sufficient by itself; retention validates all three recorded hashes and the live snapshot, then `--apply` freshly reads back the archive triplet and compares hashes immediately before local deletion.
- This package does not prune remote snapshots or automatically restore production data.
- A one-second S0.10 PostgreSQL restore duration is not service RTO; RPO/RTO values require explicit owner targets and operational evidence.
- S0.11 remains `IMPLEMENTED / BASE CI VERIFIED` until the policy-alignment exact-SHA CI, approved VPS runtime checks, external alert test, and explicit owner acceptance are complete. Timer activation and local deletion remain separately gated and are not part of this acceptance.
