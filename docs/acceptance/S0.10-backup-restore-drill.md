# S0.10 — Backup Integrity and Isolated Restore Drill Acceptance

**Implementation baseline:** `2bfdc36106df4a65dad410e8c71e91cd580de21d`
**Scope:** FlowlessHub logical backup hardening, integrity verification, off-host copy verification, and isolated PostgreSQL restore.
**Production database restore:** Out of scope and prohibited by this acceptance.
**Status:** Proposed implementation; owner execution and VPS evidence pending.

## Implementation changes

- Harden `scripts/vps/backup-db.sh` with runtime `.env` checks, PostgreSQL health checks, disk guard, backup/restore lock, private temporary output, custom-format archive validation, SHA-256, and a non-secret manifest.
- Add `scripts/vps/verify-backup.sh` to verify archive/sidecar permissions, manifest consistency, SHA-256, local PostgreSQL image availability, and `pg_restore --list` readability.
- Add `scripts/vps/restore-drill.sh` to restore to a disposable PostgreSQL 17.11 container using `--network none`, no published port, 256 MiB memory, swap disabled, 0.50 CPU, a read-only backup mount, and an ephemeral anonymous data volume.
- Validate restored database identity/size, user-schema count, user-relation count, and the `platform` schema.
- Recheck production PostgreSQL health and active-color state after the restore.
- Configure .gitattributes with `*.sh text eol=lf` so Bash scripts retain LF on Windows and Linux.
- Reuse the existing CI wildcard validation of `scripts/vps/*.sh` for Bash syntax and ShellCheck. No application image rebuild or release is required for these scripts/docs.

## Acceptance boundary

A successful `pg_restore --list` is archive readability evidence, not restore evidence. This checkpoint is only accepted after the actual `pg_restore --exit-on-error --single-transaction` completes against the isolated target and the restored database checks pass.

The script's restore duration is not the full service RTO. A single drill does not establish a production RPO; RPO depends on backup frequency and the last independently verified off-host backup. Retention, backup scheduling, off-site storage, and recurring restore cadence remain explicit operational decisions.

No step in this checkpoint may restore into the production database, stop/recreate Petshop containers, modify Petshop databases/volumes/networks/ports, alter Frictiona/Petshop Nginx vhosts, publish database ports, or perform global Docker cleanup.
