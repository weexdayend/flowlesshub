## 4. Runtime, security, and durability boundaries

Verified from the committed implementation and runbook:

- The Docker Desktop helper provisions PostgreSQL and PgBouncer inside Kubernetes; the final contract uses Kubernetes ClusterIP service DNS, not Pod-to-host routing.
- PostgreSQL storage is a bounded 2 GiB `emptyDir`. Pod replacement/deletion loses its data.
- The helper creates/reuses runtime Secrets dynamically. Secret manifests and real credential values are not committed.
- API uses PgBouncer; River worker and migration use direct PostgreSQL connections.
- API/web use ClusterIP Services and readiness/liveness probes. The worker has no fabricated HTTP health endpoint.
- Restricted Pod Security settings include non-root identities, RuntimeDefault seccomp, no service-account token mount, no privilege escalation, read-only root filesystems, and dropped capabilities.
- Production must use managed PostgreSQL/PgBouncer endpoints, a production secret manager, and immutable image references. The local `:dev` image tags are not production tags.
- S0.7 adds no public ingress, reverse proxy, TLS termination, blue/green traffic switch, or production database topology.
